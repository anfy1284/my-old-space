## 2. БАЗОВЫЕ КЛАССЫ (UI_classes.js)

### UIObject
Базовый класс всех визуальных компонентов. Свойства: `x, y, width, height, z, element`.

### Form (extends UIObject)
Окно с заголовком, кнопками управления (свернуть, развернуть, закрыть), drag/resize.
- `close()` → вызывает `this.destroy()`, удаляет DOM, диспатчит `form-destroyed`
- `destroy()` → уничтожает дочерние контролы
- `doAction(action, params)` → **Системная обработка действий**. Если `params.isStandard === true`, действие обрабатывается непосредственно в базовом классе `Form` (например, `recordOpen`, `recordAdd`, `recordDelete`, `cancel`). В противном случае (или если действие не распознано как стандартное), оно делегируется в `instance.onAction()`.
- `setFormIcon(url)` → Устанавливает иконку приложения: помещает `<img>` 16×16 в заголовок окна перед текстом (`titleIconElement`) и синхронизирует иконку кнопки в таскбаре (`_taskbarIcon`). Сохраняет URL в `this.formIcon`. Если `url` пустой — иконки скрываются.
- `setTitle(title)` → Базовая реализация: обновляет текст заголовка и диспатчит DOM-событие `form-title-changed` с `detail: { form: this }`. DataForm переопределяет (учитывает `_modified`, сохраняет `_originalTitle`) и вызывает `super.setTitle()`.

**Иконка в заголовке и таскбаре:**
| Элемент | Назначение |
|---|---|
| `titleIconElement` | `<img>` 16×16, вставляется в заголовок окна слева от текста при создании Form |
| `formIcon` | URL иконки (строка). Устанавливается через `setFormIcon(url)` |
| `_taskbarIcon` | Ссылка на `<img>` в кнопке таскбара. Устанавливается модулем `taskbar/client.js` при создании кнопки |

**DOM-событие `form-title-changed`** (диспатчится на `document` из `Form.setTitle()`):
Слушается `taskbar/client.js` для синхронизации текста кнопки в таскбаре с актуальным заголовком (включая суффикс ` *`).

### DataForm (extends Form)
Базовый класс для форм с автоматическим рендерингом из JSON layout.

**Свойства:**
| Свойство | Назначение |
|---|---|
| `controlsMap` | Плоский map **всех** созданных контролов `{name: control}`. Содержит и поля формы верхнего уровня, и каждую ячейку каждой строки табличных частей (ключи вида `ts_booking_rooms__r0__roomId`). |
| `_dataMap` | Данные формы `{fieldName: {name, value, ...}}` |
| `_datasetId` | ID серверного датасета (хранит таблицу + ID записи) |
| `_modified` | Флаг изменения данных. При `true` — заголовок с ` *` |
| `_suppressModified` | Guard для `setModified`. Когда `true` — вызов `setModified(true)` является no-op. Используется при программном обновлении полей после сохранения, чтобы DOM `input`-события не выставляли `_modified = true` обратно. |
| `_originalTitle` | Заголовок формы без суффикса ` *` |
| `appCaption` | Название приложения, установленное сервером (строка). Устанавливается через `setTitle()` в `loadLayout()` |
| `_closing` | Защита от рекурсивного закрытия (guard) |
| `_currentRecord` | Текущая выбранная запись (setter обновляет контролы) |
| `table` | Ссылка на первую `DynamicTable` (устанавливается автоматически в `renderItem`) |

**Ключевые методы:**
| Метод | Назначение |
|---|---|
| `setModified(bool)` | Устанавливает `_modified`, добавляет/убирает ` *` из заголовка |
| `setTitle(title)` | Переопределён: сохраняет `_originalTitle`, учитывает `_modified` |
| `close()` | Переопределён: если `_modified`, спрашивает "Сохранить?" через `showConfirm` |
| `doAction('save')` | Вызывает `collectData()` → `applyChanges()` → сбрасывает `_modified` |
| `doAction('cancel')` | Вызывает `this.close()` (с диалогом сохранения если `_modified`) |
| `collectData()` | Обходит `controlsMap`, собирает `{field: value}` |
| `applyChanges(data)` | Отправляет `{datasetId, changes}` на сервер |
| `loadLayout()` | Вызывает `getLayoutWithData()`, получает лейаут и данные с сервера. Применяет `both.formIcon` через `setFormIcon()` и `both.appCaption` через `setTitle()` — устанавливает иконку и название приложения |
| `renderItem(item)` | Рендерит контрол по JSON-описанию, подключает dirty-tracking. Автоматически резолвит `caption` через `__t()` если caption — объект `{ i18n: 'key' }`. |

**Жизненный цикл:**
1. `MySpace.open('uniForm', { tableName, recordID })` → создаёт экземпляр DataForm
2. `DataForm.Draw()` → `loadLayout()` → `getLayoutWithData()` → рендерит контролы
3. Пользователь редактирует → контролы вызывают `setModified(true)` → заголовок получает ` *`
4. При закрытии (X/ESC/Отмена): если `_modified` → `showConfirm("Сохранить?")` → "Да"=save+close, "Нет"=close
5. `Form.close()` → диспатчит `form-destroyed` → слушатель в DynamicTable вызывает `refresh()`

**Dirty Tracking (отслеживание изменений):**
Все контролы формы при изменении вызывают `formSelf.setModified(true)` (где `formSelf` — замыкание на DataForm):
| Контрол | Событие |
|---|---|
| TextBox, MultilineTextBox | `input` на `ctrl.element` |
| emunList (ComboBox listMode) | `input` на `ctrl.element` |
| recordSelector (TextBox + кнопка "...") | `input` на `ctrl.element` |
| CheckBox | `change` на `cb.element` |

**`_suppressModified` и программное обновление полей:**
При обновлении полей формы из кода (например, post-save refresh) DOM-события `input` на контролах будут вызывать `setModified(true)`. Чтобы этого не происходило, устанавливай `this._suppressModified = true` до обновления. `setModified(val)` проверяет: `if (val && this._suppressModified) return;`. После обновления — сбрасывай атомарно, без `finally`:
```javascript
this._modified = false;
this._suppressModified = false;
super.setTitle(this._originalTitle);
```

**Замыкание `buildBody` / `renderBodyRows` (CRITICAL):**
Метод `buildBody(bodyContainer, rows)` в `Table` передаёт `rows` (ссылку на `_dataMap[dataKey].value`) в замыкание `renderBodyRows`, которое сохраняется как `_invokeRenderBodyRows`. Это замыкание захватывает **ссылку на конкретный массив**. Если после построения таблицы заменить `DataForm._dataMap = {}` (весь объект), замыкание продолжит рендерить **старый** массив, а `data_updateValue` будет писать в новый → добавленные строки не появятся. Вывод: **никогда не заменяй весь `_dataMap`** — обновляй поля точечно: `this._dataMap[rec.name] = rec`.

### Group (extends UIObject)
Контейнер для логической группировки элементов (отрисовывается как `fieldset` с `legend`).
- `children` (Array): Список дочерних `UIObject`.
- `Draw()`: **Автоматически** проходит по массиву `this.children` и вызывает `child.Draw(this.element)` для каждого. Это основной способ создания вложенных структур.

**Флаги лейаута на группе** (`renderItem` `case 'group'` пробрасывает их на инстанс):
- `noBorder: true` → класс `ui-group-no-border`: рамка (псевдоэлементы) скрыта, `padding/margin: 0`, legend уходит в левый верхний угол. **Без caption** = невидимая группа (чистый layout-контейнер, используется в логине и каркасных группах вкладок). **С caption** → дополнительно класс `ui-group-no-border-titled` (вешается в `Draw`, когда есть текст подписи) даёт `padding-top:16px` под заголовок (отвязано от `boldCaption`).
- `boldCaption: true` → класс `ui-group-bold-caption` (жирный legend), независимо от рамки.
- `alignFields: true` (только для вертикальной группы полей) → `DataForm._renderAlignedFields`: группа рендерится как 2-колоночный CSS-grid (`ui-group-aligned`, `grid-template-columns: max-content 1fr`). Подписи дочерних контролов подавляются и выводятся отдельной ячейкой в колонке 1, сам контрол — в колонке 2; пара «подпись+контрол» лежит в ОДНОЙ grid-строке, поэтому выравнивание не разъезжается (НЕ две отдельные группы — у них высота подписи ≠ высоте поля → рассинхрон). Колонка подписей авто-ширины (по самой широкой).

Панель вкладок: каждая панель вкладки получает класс `ui-tabs-pane` (flex-колонка + `gap:14px`, как `.ui-form-content`), чтобы блоки внутри вкладки имели тот же вертикальный зазор, что и тело формы.

### Table (extends UIObject)
Базовая таблица. Поддерживает заголовки, сортировку и рендеринг строк.

- `showToolbar` (bool): Если `true`, в начале таблицы отрисовывается панель действий.
- `isTabularSection` (bool, default `false`): Автоматически определяется в `Draw()` из `appForm._dataMap[dataKey].tabularSection`. Если `true` — таблица является табличной частью (ТЧ): тулбар самостоятельно обрабатывает добавление/удаление строк без делегирования в `DataForm.doAction`.

**`data_updateParentArray(dataKey, rowIndex, colDef, newVal, displayVal)`:**  
Единая точка записи значения ячейки обратно в массив строк (`_dataMap[dataKey].value[rowIndex]`). Сохраняет `parentArr[rowIndex][colDef.data] = newVal`. Если передан 5-й аргумент `displayVal` — также сохраняет `parentArr[rowIndex]['__' + colDef.data + '_display'] = displayVal`. Это гарантирует, что display-значение FK-полей переживает ре-рендер строки (при переключении masterFor, сортировке, фильтрации). DynamicTable переопределяет метод аналогично для `dataCache`.

**`doToolbarAction(action)`:**  
Обрабатывает действие тулбара. Если `isTabularSection === true`:
- `recordAdd` → **асинхронно** запрашивает UID с сервера через `callServerMethod('drive_api', 'getNewUID', { tableName })`, затем заполняет скрытые клиентские фильтры (FK-поля из `masterFor`), добавляет строку в данные ТЧ, вызывает ре-рендер и `activateRow(rows.length - 1)` — чтобы сработал `masterFor.onRowActivate` на новой строке. Затем — `_autoStartSingleRefSelection(newRowIndex)`.
- `recordDelete` → удаляет активную строку из данных ТЧ.
- Возвращает `true` если обработано (ТЧ), `false` если нужно делегировать дальше.

**`_autoStartSingleRefSelection(newRowIndex)`:** если в ТЧ РОВНО ОДИН редактируемый ссылочный столбец (`inputType/type==='recordSelector'` + `properties.selection.table`, либо серверный `foreignKey`; `readOnly` исключаются), при добавлении строки сразу запускает выбор в него: `listMode` (выпадашка, в т.ч. когда обе кнопки) → `_openList()`; иначе `showSelectionButton` («...») → `onSelectionStart()`. Контрол ячейки регистрируется в `appForm.controlsMap['<dataKey>__r<idx>__<col>']` и рендерится асинхронно, поэтому метод ждёт его появления через `requestAnimationFrame`-ретрай. Отключается флагом `autoPickSingleRef: false` в `properties` таблицы (по умолчанию включено).

### Мастер-деталь (`masterFor`)

Контрол `Table` поддерживает механизм мастер-деталь через свойство `masterFor` в лейауте.

**Свойства в `properties` мастер-таблицы:**
| Свойство | Тип | Описание |
|---|---|---|
| `masterFor` | string \| string[] | Имя(ена) контролов-деталей (`item.name`) |
| `masterField` | string | Поле мастера (по умолчанию `'UID'`) |
| `detailField` | string | Поле детали (FK на мастер, напр. `'bookingRoomId'`) |

**Поведение при активации строки мастера (`onRowActivate`):**
1. Читает строку мастера по `rowIndex`
2. Вычисляет `displayValue` — ищет первое `__col_display` или строковое не-UID значение в строке мастера
3. Вызывает `detailTbl.setFilter(detailField, row[masterField], { type: 'client', visibility: 'hidden', operator: '=', displayValue })`

**`setFilter` с `displayValue`:** сохраняет его в объект фильтра. При добавлении новой строки в деталь `doToolbarAction` использует `displayValue` для заполнения `__<detailField>_display`, чтобы ячейка показывала имя записи мастера, а не сырой UID.

**`_isMaster = true`** — помечается на мастер-таблице. Используется в `_activateFirstRows()`.

**`_matchClientFilters(row)` — исправление:** скрытые фильтры (`visibility: 'hidden'`) всегда сравниваются по **сырому** значению поля (`raw`), не по display-значению. Видимые фильтры — по display если оно доступно.

### `_activateFirstRows()` / `renderLayout` (корневой рендер)

`renderLayout` определяет является ли вызов корневым (`layout == null`). После корневого рендера через `setTimeout(0)` вызывается `_activateFirstRows()`:
- Собирает все контролы из `controlsMap` с `activateRow` + `data_getRows`
- Сортирует: `_isMaster` первыми
- Активирует **только мастер-таблицы** (`activateRow(0)`) — детали пропускаются, их фильтры установятся через `masterFor.onRowActivate`

**Гонка `Tabs` ↔ `_activateFirstRows` (исправлено):** `Tabs.Draw` рендерит панели вкладок асинхронно (`renderAll()` с `await renderLayout(pane)` внутри; рендер ячеек/recordSelector делает **сетевые** `_fetchFkLookup`). Раньше это было «fire-and-forget» (`renderAll().catch(...)`), поэтому `await renderItem('tabs')` в корневом цикле возвращался МГНОВЕННО, корневой `renderLayout` завершался, и `setTimeout(0) → _activateFirstRows()` срабатывал **раньше**, чем таблицы внутри вкладок попадали в `controlsMap`. Итог: мастер не активировался → masterFor-фильтры не выставлялись → ТЧ-детали показывали ВСЕ строки на открытии (с одной комнатой баг невидим — отфильтровать нечего; с несколькими виден). **Фикс:** `Tabs.Draw` сохраняет `this._renderAllPromise = renderAll()...`, а `renderItem('tabs')` после `Draw()` делает `await tabsCtrl._renderAllPromise`. Так корневой цикл дожидается отрисовки всех панелей (и таблиц в них) до планирования `_activateFirstRows`. Системно чинит все табовые формы. **Общее правило:** см. анти-паттерн про async-рендер дочерних контролов.

### `tr._dataIndex` — реальный индекс строки

При рендере `renderRowElement` присваивает `tr._dataIndex = rowIndex` (индекс в исходном массиве данных до фильтрации). `activateRow` и `updateAllRowsReadOnly` используют `child._dataIndex === rowIndex` вместо визуального индекса в tbody. Это исправляет несоответствие при активных клиентских фильтрах (когда часть строк скрыта).

### Режимы редактирования таблицы (`editMode`)

Свойство `editMode` в `properties` таблицы управляет поведением клика:

| Значение | Поведение |
|---|---|
| `'row-activate'` (по умолчанию) | 1-й клик — активирует строку; 2-й клик по активной — фокусирует редактор |
| `'cell-immediate'` | 1-й клик — активирует строку И сразу переходит в режим редактирования ячейки |

**Как работает `cell-immediate` (КРИТИЧНО — все строки редактируемы):**
В этом режиме поля/кнопки активны во ВСЕХ строках, а не только в активной — активация строки нужна лишь для подсветки и как цель `recordDelete`/клавиатуры, но НЕ для редактирования. Это обеспечивается тремя точками расчёта `isActive`, каждая учитывает `editMode === 'cell-immediate'`:
1. `renderCellElement` (начальное состояние ячейки; общий метод — покрывает и `Table`, и `DynamicTable`, т.к. её `_fillRow` зовёт его же);
2. `Table.updateAllRowsReadOnly`;
3. `DynamicTable.updateAllRowsReadOnly` (виртуализированный вариант).
Формула во всех трёх: `isActive = (editMode === 'cell-immediate' || <строка активна>) && !readOnly && !colDef.readOnly`. Колонки/таблицы с `readOnly` поведения не меняют.

**CSS-видимость кнопок:** правило `.ui-dynamictable tr.ui-table-row:not(.active) .input-field-button { visibility: hidden }` прячет кнопки («...», «+», выпадашка) в неактивных строках. Чтобы в `cell-immediate` они оставались видимыми, `Table.Draw` вешает на контейнер класс `ui-table-immediate` (`if (this.editMode === 'cell-immediate')`), а CSS-правило `.ui-dynamictable.ui-table-immediate tr:not(.active) .input-field-button { visibility: visible }` (выше по специфичности) перебивает скрытие. JS при этом держит кнопки не-`disabled` (см. `isActive`), иначе сработало бы правило скрытия disabled-кнопок.

**Флаг `inTable` (выпадашка только по кнопке):** в `cell-immediate` поля редактируемы сразу, и авто-открытие списка (`listMode`) по клику/фокусу в поле мешает. `renderCellElement` проставляет контролу `cellItem.properties.inTable = true`; в `TextBox` (через `setProperties` → `this.inTable`) авто-открытие списка в обработчиках `click` (`if (this.listMode && !this.inTable)`) и `focus` (`... && !this.inTable`) подавляется — в ячейке список открывается ТОЛЬКО кнопкой выпадашки (её обработчик зовёт `_openList` напрямую, не затронут). На обычных полях формы (вне таблицы) флага нет → список открывается при активации поля, как и раньше.

**Дефолт новой строки ТЧ:** `Table.doToolbarAction('recordAdd')` пред-заполняет новый ряд значениями `col.defaultValue` из лейаута колонки (`newRow[col.data] = (col.defaultValue !== undefined ? col.defaultValue : '')`). Задавать дефолт прикладным кодом не нужно — ставь `"defaultValue": 1` прямо в колонке (напр. `count` у «Гости»/«Услуги»).

**Checkbox в `cell-immediate`:** исторически в неактивной строке checkbox был `disabled`, и `renderRowElement` (`tr.click`, `wasInactive`) после `activateRow()` доводил переключение вручную. Теперь в `cell-immediate` checkbox НЕ `disabled` → нативный/capture-путь переключает его сам и ставит `ev.__checkboxHandled = true`; ручной toggle в `tr`-обработчике защищён `&& !ev.__checkboxHandled`, иначе был бы двойной toggle (без эффекта).

**Лейаут для включения режима:**
```json
"properties": { "editMode": "cell-immediate", ... }
```

**Управление видимостью кнопок тулбара:**

- `properties.hiddenButtons: string[]` в лейауте таблицы — список action-идентификаторов кнопок, которые нужно скрыть для конкретной таблицы. Пример: `"hiddenButtons": ["listSettings", "recordOpen"]`. Читается в конструкторе Table: `this.hiddenButtons`.

### `Table.onSelectOrOpen` — алгоритм резолюции `tableName`

При двойном клике / нажатии кнопки «Открыть» в тулбаре вызывается `onSelectOrOpen(rowIndex)`.

**Алгоритм поиска tableName:**
1. Берём `this.tableName` — явный `tableName` из лейаута таблицы (свойство `properties.tableName`).
2. Если не задан — пытаемся взять из `appForm.dbTable || appForm.dataKey`.
3. **ВАЖНО:** Перед шагом 2 проверяем `_dataMap[dataKey].tabularSection === true`. Если таблица является ТЧ (встроенной таблицей записи) — **не наследуем** tableName от родительской формы; выходим сразу. Иначе ТЧ откроет форму родительской записи (баг).

**Код паттерна:**
```javascript
// В onSelectOrOpen — перед наследованием от родителя:
if (!tableName) {
    const meta = appForm._dataMap && appForm._dataMap[this.dataKey];
    if (meta && meta.tabularSection === true) return; // ТЧ не открывает форму
    tableName = appForm.dbTable || appForm.dataKey || '';
}
if (!tableName) return;
```

**CRITICAL:** Этот же баг проявляется в форме «выбора таблицы» (recordSelector открывает список, пользователь дважды кликает). Дополнительная защита — `hiddenButtons: ['recordOpen']` на такой таблице.

### `TextBox.onSelectionStart()` — открытие формы выбора

Когда TextBox имеет `inputType: 'recordSelector'` и пользователь нажимает «...», всегда вызывается `onSelectionStart`. Это системный метод, который всегда открывает:
```javascript
MySpace.open('uniForm', {
    mode: 'list',
    dbTable: <table из properties.selection.table>,
    selectMode: true,
    readOnly: true
});
```
- `selectMode: true` — в тулбаре показываются только Select/Cancel (Add/Delete скрыты автоматически через `hideInSelectMode`)
- `readOnly: true` — все поля нередактируемы
- Открывается **list**-режим (`dbTable`), не record-режим

**Следствие:** Если таблица открывается через `recordSelector`, она должна быть зарегистрирована в `layoutMemory` **как list-лейаут** (`mode: 'list'`). Регистрации только как record-лейаут недостаточно.

### recordSelector — кнопки выбора, авто-режим, открытие записи, F2

**Две кнопки поля-ссылки** (`renderItem` `case 'recordSelector'`): «...» (`showSelectionButton`, открывает форму выбора через `onSelectionStart`) и выпадашка (`showListButton` → `listMode`, инлайн-список имён). Лейаут-API (флаги в `properties`):
- задан `showSelectionButton` и/или `showListButton` → форс этих кнопок;
- НЕ задан ни один → **AUTO**: считаем видимые пользователю записи и решаем — `<10` ⇒ только выпадашка (item'ы преднагружаются), `≥10` ⇒ только «...»;
- `readOnly` → без кнопок.
Тот же механизм работает и для ячеек ТЧ (они рендерятся через тот же `renderItem`).

**`DataForm._fetchFkLookup(table)`** — кэш на форме (`_fkLookupCache`): ОДИН `getLookupList` на таблицу за открытие формы. Кэширует **in-flight промис**, поэтому параллельно рендерящиеся ячейки одной колонки делят один запрос (иначе было бы N строк × M колонок запросов). Возвращает `{ totalRows, items:[{value:UID, caption:display}] }`.

**`getLookupList`** (`uniForm` → `dynamicTableRegistry` → `globalServerContext.getLookupList`): возвращает `{ columns, rows, totalRows }`; rows нормализованы в `{ UID, display }`, где `display` = поле `name` (или первое строковое поле модели); `totalRows` = `count` через `dbGateway` с `sessionID` → **с учётом RLS** (= «что реально видит пользователь»). Поэтому критерий авто-режима точный. Выпадашка показывает только `display` (=name); кастомные фильтры сверх RLS `getLookupList` пока не применяет.

**Выпадашка (listMode) и `onChange` (исправлено):** клик по строке инлайн-списка (`_openList`) раньше слал только событие `input`. Теперь он зеркалит путь «...» (`handleSelection`): кроме `setText(value)` он вызывает `this.onChange(value, caption)` И диспатчит событие `change`. Это нужно, чтобы `events: { onChange }`, привязанный через `_wireItemEvents` (объектный колбэк `ctrl.onChange`, т.к. `onChange` НЕ в `DOM_MAP`), срабатывал и при выборе из выпадашки — напр. перезагрузка формы настроек организации по смене селектора `__orgId`. **Правило:** любой путь выбора значения в `TextBox`-селекторе обязан звать `onChange`.

**Авто-режим в автогенерируемых лейаутах:** `buildTableFieldsFromModel` (`uniForm/server.js`) для FK-полей больше НЕ форсит `showSelectionButton: true` — `field.properties` = только `{ selection }`, поэтому включается AUTO (выпадашка/«...»). Так же в `UserSettings`/`organizationSettings` `buildLayout` для ссылочных полей убран `showSelectionButton`. То есть «красота» (выпадашка для малого выбора) распространена на все автогенерируемые формы, а не только на ручной booking-лейаут.

**Открытие записи (как в 1С):**
- `TextBox.openCurrentRecord()` — `MySpace.open('uniForm', {mode:'record', tableName: selection.table, recordID: rawValue})`; no-op при пустом значении.
- `showOpenButton: true` (флаг) → кнопка «открыть» слева от «...» (системная иконка `open.png`).
- **F2** на любом ссылочном `TextBox` (есть `selection.table` + значение) → `openCurrentRecord` (в keydown-обработчике, до date/digits-веток).
- Форма списка: `DynamicTable.openRecord(globalIndex)` (вынесен из `onSelectOrOpen`) — открывает запись ВСЕГДА, в любом режиме (в т.ч. selectMode, где двойной клик выбирает). F2 в keydown строки зовёт `openRecord`.

**`TextBox._openList` — авто-закрытие и guard (CRITICAL):** выпадашка при открытии вешает `MutationObserver` (на `containerElement`/`document.body`, `subtree:true`) + обработчики `scroll/resize/wheel/pointer`, которые закрывают список при ЛЮБОЙ мутации DOM или скролле (чтобы popup не «отрывался» от поля). Поэтому ПРОГРАММНОЕ открытие во время DOM-churn (напр. masterFor-ре-рендер деталей сразу после добавления строки ТЧ) мгновенно закрывает только что открытый список. Решение — `_autoOpenGuardUntil` (timestamp): на окно ~600мс `MutationObserver` и scroll-хендлер пропускают закрытие. Ставится перед `_openList()` при авто-открытии (`_autoStartSingleRefSelection`); ручные открытия по клику не затронуты.

### `saveLayout` — режим `mode` (record vs list)

```javascript
await layoutMemory.saveLayout({
    appName: 'uniForm',
    tableName: 'my_table',
    roles: '*',
    mode: 'list',    // 'list' | 'record' (по умолчанию 'record')
    layout: [ ... ],
    events: {
        onLoadData: async (params, ctx) => { ... return []; }  // для виртуальных list
    },
    clientScript: uid  // только для record
});
```

- `mode: 'record'` — лейаут используется при открытии `{ tableName, recordID }`
- `mode: 'list'` — лейаут используется при открытии `{ dbTable }`. uniForm проверяет `customLayout.events.onLoadData` и вызывает его для загрузки строк.

**ВАЖНО:** Для виртуальных таблиц, которые будут открываться через `recordSelector`, нужно регистрировать **оба** режима — иначе либо список пустой (list нет), либо открытая запись не редактируется (record нет).

### `uniForm/server.js` — list-режим с кастомным `onLoadData`

В ветке `isListMode` (`getLayoutWithData`):
- Если у кастомного list-лейаута есть `events.onLoadData` — он вызывается с `(params, ctx)`.
- Результат передаётся как `data` в ответ вместо `data: []`.
- Лейаут клонируется через `JSON.parse(JSON.stringify(...))` перед вставкой данных (защита от мутации кэша).

Это позволяет регистрировать **виртуальные таблицы** — списки без реальных DB-моделей, формируемые из произвольных источников (другая БД, агрегация, конфиг).

### Динамический шаблон `{field}` в `properties.selection.table`

В `renderCellElement` поддерживается шаблон `{fieldName}` в строке `selection.table`:

```json
{
    "data": "recordId",
    "inputType": "recordSelector",
    "properties": {
        "selection": {
            "table": "{tableName}",
            "idField": "UID",
            "displayField": "name"
        }
    }
}
```

Когда `selection.table` содержит `{fieldName}`:
- При рендере ячейки создаётся геттер через `Object.defineProperty`, который читает `row[fieldName]` каждый раз при обращении.
- Это позволяет кнопке «...» каждой строки открывать таблицу, соответствующую значению поля `tableName` в **этой же строке**.
- Работает в `cell-immediate` режиме: каждая строка может открывать разную таблицу.

**Требование:** Поле-источник шаблона (`tableName` в примере) должно быть в той же строке данных, т.е. присутствовать в объекте строки (в `_dataMap[key].value[rowIndex]`).

### DynamicTable (extends Table)
Таблица с серверной подгрузкой данных по частям, SSE-обновлениями и виртуальным скроллом.

**Подход: pre-allocated rows (все строки в DOM)**  
Все `<tr>` создаются в DOM сразу при получении `totalRows` с сервера. Строки пустые (placeholder) до момента попадания в вьюпорт. Скроллбар браузера отражает полный датасет без какой-либо математики позиционирования.

**Ключевые свойства:**

| Свойство | Назначение |
|---|---|
| `totalRows` | Общее число строк датасета (от сервера) |
| `dataCache` | Кэш загруженных строк `{ globalIndex: record }` |
| `_rowElements` | Массив всех `<tr>` элементов, индекс = globalIndex |
| `_activeRowIndex` | **Глобальный** индекс активной строки (= globalIndex) |
| `firstVisibleRow` | Глобальный индекс первой видимой строки (для запроса следующей страницы) |
| `bufferRows` | Число строк-буфера выше и ниже вьюпорта (по умолчанию 10) |
| `rowHeight` | Высота строки в px (по умолчанию 25) |
| `editSessionId` | ID редакторской сессии (возвращает сервер) |

**Ключевые методы:**

| Метод | Назначение |
|---|---|
| `buildBody()` | Создаёт обычную `<table>` с пустым `<tbody>`, сохраняет `_mainTbody`, `_dtBcolgroup` |
| `_allocateRows()` | Создаёт/дополняет `_rowElements[]` до `totalRows` TR-плейсхолдеров |
| `_fillRow(globalIndex)` | Заполняет TR ячейками из `dataCache[globalIndex]`, ставит `tr._dtFilled = true` |
| `_emptyRow(tr)` | Сбрасывает TR в placeholder (`_dtFilled = false`) |
| `_fillVisibleRows()` | Заполняет все кешированные строки в диапазоне scrollTop±buffer |
| `_resetFilledRows()` | Сбрасывает все `_dtFilled` флаги (O(N), без DOM) — вызывается при `refresh()` |
| `_onScroll()` | Сначала `_fillVisibleRows()`, потом запрашивает у сервера недостающие строки |
| `activateRow(globalIndex)` | O(1): снимает класс `active` с предыдущего TR, ставит на `_rowElements[globalIndex]` |
| `deactivateRow()` | Снимает `active`, очищает `_docKeyHandler` |
| `updateAllRowsReadOnly()` | Итерирует только видимый диапазон (не все N строк) |
| `onSelectOrOpen(globalIndex)` | Прямой `dataCache[globalIndex]` → открывает uniForm или срабатывает selectMode |
| `refresh()` | `dataCache = {}` + `_resetFilledRows()` + `loadData()` |
| `loadData(firstRow)` | Загружает страницу данных, после получения: `_allocateRows()` + `_fillVisibleRows()` |

**Важно:**  
`_activeRowIndex` — это **глобальный** индекс (= позиция в `_rowElements[]` = ключ в `dataCache`).  
Формула `firstVisibleRow + _activeRowIndex` **не используется** — все операции работают непосредственно с globalIndex.

**SSE:**  
При мутации данных на сервере приходит SSE-событие → `dataCache = {}` + дебаунсированный `refresh()` (300мс) на всех подписчиках. Дебаунс (`_sseRefreshTimer`) группирует множественные SSE-события в один `refresh()`, предотвращая каскадные перезагрузки.

**`destroy()`** очищает: `_scrollDebounce`, `_sseRefreshTimer`, `_scrollHandler`, `_resizeObserver`, `_docKeyHandler`, `_rowElements`, SSE EventSource.

## 2.1. ПАТТЕРН `onBeforeSave` И PIPELINE РАСЧЁТОВ

### Хук `onBeforeSave`

Серверный хук, вызываемый фреймворком **ДО** записи изменений в БД. Объявляется как метод экспортируемого объекта в `forms/<tableName>.server.js`.

**КРИТИЧНО: `record` всегда `null`**
Параметр `record` в хуке всегда приходит пустым (`null`). Полный объект записи нужно загружать из БД самостоятельно через `parentUID`:

```js
async onBeforeSave({ record, changes, tabularSections, parentUID }, ctx) {
    // record — всегда null! Используй parentUID для загрузки из БД
    const bookingId = parentUID || (changes && changes.UID);
    let dbRecord = null;
    if (bookingId) {
        dbRecord = await modelsDB.Bookings.findByPk(bookingId, { raw: true });
    }
    // Смерджить базовые данные с изменениями
    const effective = Object.assign({}, dbRecord || {}, changes || {});
}
```

**Параметры:**
| Параметр | Тип | Описание |
|---|---|---|
| `record` | `null` | Всегда null (не использовать!) |
| `changes` | `Object` | Только изменённые поля основной записи |
| `tabularSections` | `Object` | Актуальные данные всех ТЧ `{ tableName: row[] }`. Читать и писать сюда — фреймворк сохранит их после хука. |
| `parentUID` | `string` | UID основной записи (всегда актуален, в т.ч. для новых записей) |
| `ctx` | `Object` | `{ sessionID, user, role }` |

**Запись в `tabularSections`:**
Если хук присваивает `tabularSections.some_table = newRows`, фреймворк сохранит эти строки вместо данных из клиента. Это основной способ серверного пересчёта ТЧ (например, `invoice_lines`).

### Pipeline расчёта строк счёта (`_buildInvoiceLines`)

Внутренний хелпер в `apps/booking/forms/bookings.server.js`, принимает предзагруженные данные ТЧ и рассчитывает строки счёта в памяти:

**Входные данные:**
- `rooms` — массив строк ТЧ `booking_rooms` с уже заполненными UID и `roomId`
- `guests` — массив строк ТЧ `booking_guests`, связанных с rooms через `bookingRoomId`
- `roomServices` — массив строк ТЧ `booking_room_services`, связанных через `bookingRoomId`
- `checkIn` / `checkOut` — даты из основной записи

**Загружает из БД:** `GuestTypes`, `Rooms`, `RoomPrices`, `Services`, `ServicePrices`, `ServiceTaxComponents`, `TaxCategories`, `TaxRates`

**Алгоритм по каждому номеру:**
1. Фильтрует гостей и услуги по `bookingRoomId === room.UID`
2. Суммирует гостей по возрастным **бакетам** (по `gt.ageFrom`): `adults` (16+), `teen14_15` (14–15), `kids6_13` (6–13), `kids3_5` (3–5), `kids2` (2), `infants` (0–1). Границы бакетов совпадают с границами ВСЕХ ценовых полос (завтрак 13/14, курсбор 15/16) — см. «Возрастные полосы» ниже.
3. `billingGuests` (заполняемость номера для тарифа проживания) = гости **6+** (`adults + teen14_15 + kids6_13`). Дети <6 идут флэт-тарифом и в загрузку номера НЕ считаются.
4. Ищет тариф `RoomPrices` по `roomId + guestsCount(=billingGuests) + dateFrom/dateTo` (диапазон содержит дату заезда). **Брони не имеют FK на `room_prices`** — тариф резолвится по дате в момент расчёта; поэтому период, отсутствующий в `room_prices`, тихо ломает пересчёт старых броней (сид обязан сохранять легаси-периоды, см. ниже).
5. Генерирует строки: проживание; дети 2–5 (флэт-цена/ночь); курортный сбор (взрослые / 6–15 = `kids6_13 + teen14_15`); услуги ТЧ (завтрак/собака — по возрастным полосам `service_prices`); финальная уборка — **только при `nights ≤ 3`** (Endreinigung, цена по комнате из `service_prices`; иначе включена в тариф). Суммы курсбора и детского тарифа берутся из `service_prices` (`srv-kurbeitrag` / `srv-child`), а НЕ числом в коде (де-хардкодинг сумм; правило «кто и когда платит» + порог `3` пока в коде — техдолг, Шаг 2 = флаг `autoApply` во фреймворке).
6. Каждой строке ставка НДС присваивается **не числом**, а резолвится из налоговой группы по дате заезда (см. ниже)
7. Услуги с налоговыми компонентами разворачиваются в несколько строк счёта (по одной на ставку)

**Возрастные полосы (CRITICAL):** услуга с возрастными ценами (`service_prices.ageFrom/ageTo`) матчится к бакету гостя **полным покрытием**: `sp.ageFrom ≤ gt.ageFrom AND (sp.ageTo == null OR sp.ageTo ≥ gt.ageTo)`. Если граница ценовой полосы проходит ВНУТРИ возрастного бакета (полоса не накрывает бакет целиком) — ни одна полоса не матчится и начисление по этому бакету **молча выпадает** из счёта. Поэтому `guest_types` обязаны быть разбиты по ВСЕМ ценовым границам всех правил сразу. Для Seiler это границы 2, 3, 6, 14, 16 (завтрак режет по 13/14, курсбор — по 15/16), отсюда отдельный бакет `teen14_15`. Завтрак Seiler: полосы `3–5 / 6–13 / 14–99` ↔ бакеты `kids3_5 / kids6_13 / {teen14_15, adults}`.

**Критичный момент:** `g.count` должно быть `Number`, не строкой. Обеспечивается через `"inputType": "number"` в колонке лейаута → `TextBox.digitsOnly=true` → `getValue()` возвращает `Number`.

**Услуги с `count=0` (checkbox):** Если колонка `count` в `ts_booking_room_services` использует `"inputType": "checkbox"`, `getValue()` возвращает `true`/`false`. В `onBeforeSave` выполняется нормализация `boolean → 0/1` ДО вызова `_buildInvoiceLines`. Внутри `_buildInvoiceLines`: `const cnt = Number(rs.count); if (!cnt) continue;` — строки с `count=0` полностью пропускаются.

**Сортировка:** Перед возвратом строки сортируются по `label` локалью `'de'`:
```js
lines.sort((a, b) => (a.label || '').localeCompare(b.label || '', 'de'));
```
Сортировка выполняется только над строками текущего счёта в памяти — не касается БД.

### Налоговая модель (НДС/MwSt): группы, ставки по датам, дробление

Ставки НДС **не зашиты числами** ни в коде, ни в таблицах-источниках (`services.taxRate` и `room_prices.taxRate` удалены). Ставка — это данные.

**Справочники (глобальные, `excluded_tables` в `app.config.json`, сид в `apps/common/db/defaultValues.json`):**
- `tax_categories` — налоговые группы: `accommodation`, `food`, `beverage`, `standard`, `reduced`, `exempt` (фикс. UID `000000000-tax-cat-000X`, поле `code` для резолва).
- `tax_rates` — ставка группы с датами действия (`taxCategoryId`, `rate`, `validFrom`, `validTo`). Напр. `food` = 19% до 31.12.2025 и 7% с 01.01.2026 (реформа в Германии); `beverage` = 19%; `accommodation`/`reduced` = 7%; `exempt` = 0%; `standard` = 19%.

**Привязка:** `services.taxCategoryId` (NOT NULL) и `service_tax_components.taxCategoryId` ссылаются на группу.

**Резолв ставки** (`bookings.server.js`): `resolveRate(categoryId, fallback)` ищет в `tax_rates` строку группы, действующую на **дату заезда** (`validFrom ≤ checkIn ≤ validTo`, при нескольких — с самым поздним `validFrom`); `rateByCode(code, fallback)` — то же по коду группы; `svcRate(svc)` — ставка услуги из её группы. Проживание/дети/курсбор/уборка резолвятся через `accommodation`/`exempt`. Числовой фолбэк в коде — только `0` (страховка при отсутствии данных).

**Дробление услуги на несколько ставок (`service_tax_components`):** ТЧ-справочник услуги (поля `name`, `taxCategoryId`, `splitMode` = `percent`/`amount`/`remainder`, `splitValue`, `validFrom`/`validTo`, `displayOrder`). Хелпер `splitLineByComponents` делит готовую строку на уровне `unitPrice`:
- `percent` — `splitValue`% от цены; `amount` — фикс. сумма за единицу; `remainder` — остаток (поглощает округление, гарантирует Σ частей = исходной сумме).
- `emitServiceLine` применяет только компоненты, действующие на дату заезда (`componentApplies`). Нет действующих → строка остаётся одной (ставка из группы услуги). Подпись строки: `«<услуга> – <name компонента>»`.
- Пример (Seiler, с 01.01.2026): завтрак → `Speisen` (group `food`, 70%, 7%) + `Getränke` (group `beverage`, 30%, 19%). Брони до 2026 — единая строка `standard` 19% (компоненты с `validFrom=2026-01-01` не действуют).

**Снимок в счёте:** `invoice_lines.taxRate` хранит уже **зафиксированный** % (результат резолва на момент формирования) — единственное место, где ставка осознанно остаётся числом (счёт — документ на дату). Шаблон `apps/reports/invoice/template.js` группирует строки по этому `taxRate` для итогов «davon MwSt. X%» — менять его при дроблении не нужно.

> Полные доменные правила цен/НДС: `ПРАВИЛА_ЦЕНООБРАЗОВАНИЯ.md` (корень проекта). Краткая конвенция «не хардкодить ставки»: `CLAUDE.md`.

### Таблица услуг по умолчанию (`hotel_default_services`)

Настроечная таблица в `apps/common/db/db.json`. Хранит набор услуг, автоматически появляющихся в ТЧ `booking_room_services` при создании брони.

**Поля:** `organizationId`, `hotelId`, `serviceId` (FK→services), `displayOrder`

**Данные Seiler:** `hds-seiler-breakfast` (Frühstück), `hds-seiler-pet` (Gebühr für den Hund) — вносятся через `scripts/generate_demo_base.js`.

**Серверная функция `getDefaultServices({hotelId}, ctx)`** в `bookings.server.js` — возвращает `{ services: [{ serviceId, serviceName }] }` для указанной гостиницы.

**Клиентская автозаполнение:** `onGuestRowActivated` в `bookings.client.js` — срабатывает через `events.onRowActivate` на `ts_booking_guests`. Логика:
1. Определяет `bookingRoomId` активной строки из `ts_booking_rooms`

3. Вызывает `getDefaultServices({hotelId})` с сервера
4. Для каждой услуги получает UID через `drive_api.getNewUID` → добавляет строку с `count: false` (checkbox off)
5. Вызывает `_invokeRenderBodyRows()` для ре-рендера, затем `setModified(true)`

## 3. ПРОЦЕСС СОЗДАНИЯ ПРИЛОЖЕНИЙ (APPS)

Любое новое приложение должно быть зарегистрировано и оформлено по следующим правилам:

### Регистрация (ОБЯЗАТЕЛЬНО)
Чтобы сервер (loadApps) увидел приложение, его необходимо добавить в `drive_forms/apps.json`:
```json
{
  "name": "myAppName",
  "path": "/myAppName"
}
```

### Конфигурация (config.json)
- `autoStart: true` — скрипт client.js будет загружен в браузер при старте.
- `access: ["admin", "user", "public"]` — определяет доступность приложения.

### Клиентская часть (resources/public/client.js)
Должна использовать паттерн `MySpace.register` с методом `createInstance`. Пример:
```javascript
MySpace.register("myApp", {
    config: { allowMultipleInstances: true },
    createInstance: async function(params) {
        const appForm = new DataForm("myApp");
        const instance = {
            onOpen: async (p) => { await appForm.Draw(); },
            onAction: (action, p) => { /* логика */ }
        };
        appForm.instance = instance;
        await instance.onOpen(params);
        return instance;
    }
});
```

### Взаимодействие doAction (АНТИ-РЕКУРСИЯ)
Фреймворк использует каскадную обработку: `Form.doAction` → `instance.onAction`.
**КАТЕГОРИЧЕСКИ ЗАПРЕЩЕНО** в `instance.onAction` вызывать `appForm.doAction`, если вы не обрабатываете действие сами. Это создаёт бесконечную петлю. Если приложение не знает как обработать действие — оно должно просто выйти из функции (вернуть `false`/`undefined`). Фреймворк сам найдет стандартную реализацию.

### Стандартные контролы
- **Button:** Обычная кнопка. Использует `action` и `params` для вызова `doAction` через `onClick`.
- **TextBox, CheckBox, ComboBox (emunList):** Стандартные поля ввода.
- **Tabs:** Панели с вкладками, рендерят лейаут через `renderLayout`.
| Класс | Назначение | getValue() |
|---|---|---|
| `TextBox` | Текстовое поле | Для `showSelectionButton` → `rawValue` (FK ID); для `isDate` → ISO `"yyyy-mm-dd"` или `null`; для `digitsOnly` → `Number` (или `null` если пусто); иначе → `getText()` |
| `MultilineTextBox` | Многострочное поле | `getText()` |
| `CheckBox` | Флажок | `getChecked()` → `boolean` |
| `ComboBox` | Выпадающий список | `getText()` |
| `DatePicker` | Выбор даты | `getValue()` → `Date` |
| `Button` | Кнопка | N/A |
| `Group` | Группировка контролов | N/A |

### TextBox — числовой режим (`digitsOnly`)

Активируется, когда `renderItem` получает `item.type === 'number'` (или когда `Table.renderCellElement` копирует `col.inputType → cellItem.type`).

**Флаг `digitsOnly`:** выставляется в конструкторе TextBox при `item.type === 'number'`. Включает числовой режим ввода.

**`getValue()` возвращает `Number` (не строку):**
```js
if (this.digitsOnly) {
    const txt = this.getText();
    if (txt === '' || txt === null || txt === undefined) return null;
    const n = Number(txt);
    return isNaN(n) ? txt : n;
}
```
Это единственная точка принуждения типа. НЕ нужно конвертировать числа в `parseInt`/`Number()` в прикладном коде.

**Требование в лейауте:** Чтобы TextBox в ячейке таблицы создавался с `digitsOnly`, колонка лейаута **ОБЯЗАНА** иметь `"inputType": "number"`:
```json
{ "caption": "Количество", "data": "count", "width": 80, "inputType": "number" }
```
Без `inputType` TextBox создаётся без `digitsOnly`, и `getValue()` вернёт строку. Тогда арифметика `0 + "2" = "02"` — строковая конкатенация.

**`Table.renderCellElement()` — маппинг `inputType → type`:**
При рендере редактируемой ячейки перед созданием контрола выполняется:
```js
if (!cellItem.type && cellItem.inputType) cellItem.type = cellItem.inputType;
```
Это гарантирует, что `renderItem` получит `item.type === 'number'` и создаст TextBox с `digitsOnly`.

**КРИТИЧЕСКИ ВАЖНО — разница между полем формы и колонкой таблицы:**

| Место | Правильный синтаксис | Неправильно |
|---|---|---|
| Колонка таблицы (ТЧ) | `"inputType": "number"` | `"type": "number"` |
| Поле верхнего уровня формы | `"type": "number"` | `"type": "textbox"` + `"inputType": "number"` |

`inputType` обрабатывается ТОЛЬКО в `Table.renderCellElement` и НЕ передаётся в `renderItem` для полей формы. Если для поля формы указать `"type": "textbox"` + `"inputType": "number"` — `renderItem` видит `type === 'textbox'`, `digitsOnly` не ставится, буквы не блокируются, а пустое поле отдаёт `""` вместо `null`. Следствие: `SequelizeDatabaseError: неверный синтаксис для типа double precision: ""`.

Итог: `getValue()` с `digitsOnly=true` возвращает `null` для пустого поля — это автоматически защищает от ошибки PostgreSQL при `allowNull: true`. Никакой дополнительной санитизации в dbGateway для числовых полей не нужно — достаточно правильного `type` в лейауте.

### TextBox — целочисленный режим со спиннерами (`integer`)

Тип `integer` — это `number` (`digitsOnly`) + `allowFloat: false` + кнопка-спиннер «+» (ТОЛЬКО плюс). Цель: быстро набирать маленькие числа (1, 2, 3…) мышью; одну кнопку легче нажать, чем пару. Уменьшение — с клавиатуры (намеренно убрали «−»).

**Поле формы:** `"type": "integer"`. **Колонка ТЧ:** `"inputType": "integer"` (тот же маппинг `inputType → type` в `renderCellElement`, что и у `number`).

**`renderItem` `case 'integer'`** (fall-through в `'number'` → `'textbox'`): ставит `properties.digitsOnly = true; properties.allowFloat = false; properties.spinButtons = true` (если не задано явно).

**Кнопка-спиннер (`TextBox.Draw`):** при `this.spinButtons && this.digitsOnly && !this._spinWrap` в `inputContainer` (тот же слот, что «...») добавляется одна квадратная кнопка `.input-field-button.ui-spin-button` с `dataset.role = 'spin-up'` (`this._spinWrap = { plus }`). Клик → `TextBox._spinValue(+step)`: `parseInt` текущего значения (пусто/NaN → 0), `+= delta`, клампинг по `minValue`/`maxValue` (если заданы) и по `allowNegative`, `setText`, затем диспатч `input` + `change` и вызов `onChange`. Через `input` срабатывает штатный обработчик ячейки ТЧ (`data_updateParentArray`) — отдельная логика не нужна.

**Свойства TextBox** (из `properties`): `spinButtons` (bool), `step` (по умолчанию 1), `minValue`/`maxValue` (nullable). Размер кнопок — CSS `aspect-ratio: 1/1` (`.input-field-button`), JS-синхронизация ширины не нужна. В неактивной строке ТЧ кнопки гасятся штатно (`applyReadonlyToElement`: `disabled` + `visibility:hidden` в DynamicTable, т.к. `dataset.role` ≠ `'selection'`).

**Сервер:** `buildTableFieldsFromModel` маппит `INTEGER → 'integer'` (а не `'number'`), `mapInputTypeToControl` — `'integer' → 'integer'`. Поэтому целые поля в автогенерируемых формах/ТЧ получают спиннеры автоматически. FK-поля (`foreignKey`) проверяются раньше → у них `recordSelector`, не `integer`. Денежные/float-поля (DECIMAL/DOUBLE) под `INTEGER` не попадают → без спиннеров. `number` остаётся float-совместимым типом без спиннеров.

### `setHidden` — корневой элемент + aligned-подпись (`UIObject`)

`UIObject.setHidden(hidden)` прячет/показывает контрол. Две тонкости:
- **Корневой элемент.** У input-контролов (TextBox и т.п.) в лейаут вставляется обёртка `this.containerElement` (рамка с полем и кнопками), а `this.element` — внутренний `<input>`. `setHidden` прячет `this.containerElement || this.element` (НЕ только `this.element`) — иначе пустая рамка остаётся в потоке (в grid занимает ячейку и сдвигает соседей).
- **Aligned-подпись.** В группе с `alignFields: true` подпись рендерится `_renderAlignedFields` отдельным `<label>`-элементом в соседней grid-колонке (контрол рисуется без своей инлайн-подписи). Чтобы скрытие контрола убирало и подпись, `_renderAlignedFields` после `renderItem` находит контрол в `controlsMap` и сохраняет `ctrl._alignedLabel = lab`; `setHidden` прячет и его. Иначе скрытая строка оставляет осиротевшую ячейку-подпись и ломает выравнивание.

### `_renderAlignedFields` / `alignFields` (2-колоночный grid)

Группа с `"alignFields": true` (класс `ui-group-aligned`) рендерит детей как 2-колоночный CSS-grid: колонка 1 — подписи (`<label class="ui-aligned-label">`, с `':'`), колонка 2 — контролы без своей инлайн-подписи (`Object.assign({}, child, { caption: '' })`). Каждая пара «подпись+поле» — в ОДНОЙ grid-строке, поэтому не разъезжаются по высоте. Подписи и поля выровнены по колонкам. Эталон — `apps/login/forms/login.layout.json` (поля в `alignFields`-группе, кнопка — сиблингом ПОСЛЕ группы).

### Form.setSizeToContent / setAnchorToWindow (авторазмер + центрирование)

`Form.setSizeToContent({ padW, padH, minWidth, minHeight })` подгоняет окно под контент: измеряет `contentArea.scrollWidth/scrollHeight`, ставит `width/height = max(min*, content + pad*) + titleH`, обновляет высоту `contentArea`, и в конце **репозиционирует, если задан якорь** (`if (this.anchorToWindow) this.updatePositionOnResize()`).

`setAnchorToWindow('center'|'bottom-right'|null)` сам позицию НЕ меняет — лишь ставит `this.anchorToWindow` и вешает `window 'resize'` → `updatePositionOnResize` (центрирует по `window.innerWidth/Height` с учётом `Form.topOffset/bottomOffset`). **Порядок (КРИТИЧНО):** `setAnchorToWindow('center')` ДО `setSizeToContent` — иначе `setSizeToContent` не перецентрирует (якорь ещё не задан), и окно останется в 0,0. Паттерн (login): `Draw()` → `setTitle` → [hide/modal] → `setAnchorToWindow('center')` → `setSizeToContent({ minWidth:320, padH:12 })`; при динамической смене контента (re-render формы) — вызывать обе повторно.

### Default-кнопка формы (Enter)

Флаг `"default": true` (или `"isDefault": true`) на элементе-кнопке лейаута → нажатие **Enter** в форме «нажимает» эту кнопку (напр. login «Sign in»).

- `renderItem` `case 'button'`: при `item.default === true` сохраняет `this._defaultButton = btn` и вешает CSS-класс `ui-default-button` (утолщённая рамка Win95).
- `DataForm._setupDefaultButtonHandler()` (вызывается в конце корневого `renderLayout`, если есть `_defaultButton`): вешает `keydown` на `this.element` в **bubble-фазе** (чтобы capture-обработчики попапов/выпадашек получали Enter раньше). На `Enter` (без модификаторов, не в `textarea`, кнопка не `disabled`) — `ev.preventDefault()` + `btn.element.click()`. Выпадашки/формы выбора живут в `document.body` вне `this.element`, поэтому их Enter сюда не доходит.
- **Сброс на ре-рендере:** в начале корневого `renderLayout` (`isRoot`) делается `this._defaultButton = null` — чтобы ре-рендер в лейаут без default-кнопки (login → смена пароля) не оставил Enter привязанным к detached-кнопке. Обработчик читает `_defaultButton` динамически на каждый Enter.
- `DataForm.destroy()` (новый оверрайд) снимает слушатель и зовёт `super.destroy()`.

### Резолюция `{ i18n: 'key' }` объектов в captions

Подписи (captions) в `db.json` и лейаутах могут храниться двумя способами:
- Строка: `"caption": "Название"` — используется как есть
- Объект: `"caption": { "i18n": "Name" }` — резолвится через `__t('Name')` на клиенте

**Где происходит резолюция:**
1. **Сервер (основной путь)** — лейаут переводится при выдаче клиенту ДВУМЯ переводчиками, оба рекурсивно заменяют `{i18n:key}` на строку:
   - `layoutMemory.translateLayoutCaptions(nodes, tFn)` (в `getLayoutForUser`, когда передан sessionID) — обходит `node.layout`, `node.columns`, `node.options`, `node.extraButtons`, **`node.tabs`**.
   - `uniForm.translateLayoutI18n(items, sessionID)` (в `getLayoutWithData` перед отдачей) — обходит `item.caption`, `item.options[].caption`, **`item.columns[]`**, `item.layout[]`, `item.tabs[].layout[]`.
   - **CRITICAL:** оба ДОЛЖНЫ обходить один и тот же набор ветвей. Исторически первый не заходил в `tabs`, второй — в `columns`; из-за этого заголовки колонок таблиц **внутри вкладок** проваливались между переводчиками и отображались сырыми ключами. При добавлении нового контейнерного типа узла (`tabs` и т.п.) обнови ОБА переводчика.
2. **Клиент (fallback)** — если caption всё ещё объект: `DataForm.renderItem` (поле формы — через `__t`), заголовки колонок таблицы (`<th>` + сортировка, `__t`), `case 'tabs'` (подписи вкладок через `__t`).

Это автоматическое поведение. При формировании лейаутов на сервере безопасно использовать `{ "i18n": "key" }` в `caption` — переводчики/клиент резолвят их сами.

**ВАЖНО:** В серверном коде (tForSession) тот же ключ используется через `tForSession(key, sessionID)`. Клиент и сервер должны использовать одни и те же ключи в одних и тех же `i18n.json`.



Добавлен в `renderItem` как `case 'htmlViewer'`. Создаёт sandboxed `<iframe>` для отображения HTML-контента (отчёты, предпросмотр документов).

## 3. КОММУНИКАЦИЯ КЛИЕНТ-СЕРВЕР

### RPC
```
callServerMethod(appName, methodName, params)
  → POST /app/call { app, method, params }
  → invokeAppMethod(app, method, params, sessionID, cb, req, res)
  → appModule[methodName](params, sessionID, req, res)
```
Первый аргумент серверного метода — **один объект** `params`.

### Dataset (контекст между вызовами)
```javascript
// Сохранение:
const id = dataApp.storeDataset({ table: 'organizations', id: 42, ... });
// Получение:
const ds = dataApp.getDataset(id); // → { table, id, ... }
```

### uniForm: серверные методы
| Метод | Параметры | Назначение |
|---|---|---|
| `getLayoutWithData` | `{ tableName, recordID }` или `{ dbTable }` или `{ datasetId }` | Список-режим (`dbTable`): возвращает DynamicTable-лейаут. Запись-режим: генерирует layout + данные + datasetId. Вариант с `datasetId` (без `tableName`) — для post-save refresh. |
| `generateFormSpec` | `(tableName, params)` | Строит layout из метаданных модели; при новой записи — pre-генерирует UID |
| `applyChanges` | `{ datasetId, changes }` | Извлекает таблицу/ID из dataset; делает UPDATE или CREATE в зависимости от флага `isNew`; возвращает `{ ok: true, recordId: parentUID }` |

### uniForm: pre-генерация UID для новых записей

**Проблема:** При открытии формы для новой записи (`recordID` не задан) UID присваивался только в момент сохранения (`Model.create`). Это не позволяло форме показывать UID до записи в БД.

**Решение (паттерн `isNew` + pre-generated UID):**

```
generateFormSpec (recordID не задан)
  → _util.generateUID(modelName)     — генерируем UID тем же алгоритмом, что и dbGateway
  → data[UID].value = effectiveRecordId  — вставляем в поле UID формы
  → dataApp.storeDataset({ id: effectiveRecordId, isNew: true, ... })
```

```
applyChanges
  → dsObj.isNew === true   → operation: 'create'
    changes.UID не задан   → changes = { UID: recordId, ...changes }  (подставляем pre-generated)
  → dsObj.isNew === false  → operation: 'update' (стандартный путь)
```

**Защита в `drive_root/dbGateway.js` executor:**
```javascript
if (!data.UID) {          // генерировать ТОЛЬКО если UID ещё не задан
    data.UID = util.generateUID(Model.name);
}
```
Если pre-generated UID передан в `data.UID` — он сохраняется без изменений.

**Ключевые принципы:**
- UID генерируется **один раз** на сервере при открытии формы, до записи в БД.
- Флаг `isNew: true` хранится в датасете и является единственным источником истины о статусе записи (новая/существующая). Не полагайся на наличие/отсутствие `recordId` в `applyChanges` — к этому моменту `id` в датасете уже заполнен.
- В БД запись НЕ создаётся при открытии формы — только при сохранении.

## 6. dbGateway — ЕДИНАЯ ТОЧКА ДОСТУПА К БД

### Назначение
Все операции чтения/записи бизнес-данных проходят через `dbGateway.execute()`. Это позволяет перехватывать, проверять, модифицировать или блокировать запросы на любом уровне.

### Архитектура (каскадные middleware)
```
ЗАПРОС → [APP middleware] → [FORMS middleware] → [ROOT middleware] → EXECUTOR (Sequelize) → РЕЗУЛЬТАТ
```

Три уровня middleware:
| Уровень | Файл | Назначение |
|---|---|---|
| `app` | Регистрируется в `server.js` приложения | Бизнес-логика конкретного приложения |
| `forms` | `drive_forms/dbGateway.js` | Проверки сессий, прав, общие для форм |
| `root` | `drive_root/dbGateway.js` | Системные проверки, аудит, rate-limiting |

### API

**`dbGateway.execute(request)`** — выполнить запрос к БД через цепочку middleware.

```javascript
const result = await dbGateway.execute({
    operation: 'read',              // 'read'|'findByPk'|'findOne'|'count'|'create'|'update'|'delete'
    table: 'organizations',         // имя таблицы (как в БД)
    where: { id: 5 },              // условия (опционально)
    data: { name: 'Test' },        // данные для create/update (опционально)
    options: {                      // опции Sequelize (опционально)
        order: [['name', 'ASC']],
        limit: 20,
        offset: 0,
        raw: true,
        transaction: t             // для транзакций
    },
    context: {                      // контекст вызова (опционально)
        sessionID: 'abc',
        userId: 42,
        appName: 'uniListForm'
    }
});
```

**`dbGateway.use(level, fn)`** — регистрация middleware.

```javascript
// Сигнатура middleware:
async function myMiddleware(request, next) {
    // Изменить request...
    const result = await next(request);  // передать дальше
    // Изменить result...
    return result;
}

dbGateway.use('app', myMiddleware);
```

### Executor (конечная точка)
Расположен в `drive_root/dbGateway.js`. Преобразует `request` в вызов Sequelize.

**Ключевые механизмы:**
1.  **Санитизация данных:** Перед сохранением (create/update) пустые строки `""` → `null` для полей: с внешними ключами (`references`, иначе Postgres падает на FK) И nullable-полей с валидаторами (`attr.allowNull && attr.validate`). Второе нужно для полей вроде `email` (`isEmail`): Sequelize пропускает валидаторы только при `null`, а на `""` гоняет `isEmail` и роняет save. Условие: `data[k] === "" && attr && (attr.references || (attr.allowNull && attr.validate))`. (`attr.validate` доходит до рантайм-модели, т.к. `createDB.js` копирует определение поля целиком — `fields[field] = { ...opts, type }`.)
2.  **Генерация UID:** Присваивает `UID` новым записям. В качестве ключа хэша всегда используется `Model.name`.
3.  **Инвалидация FK-кэша:** После каждой мутации (create/update/delete) executor вызывает `globalServerContext.invalidateFkCache(Model.tableName)`, чтобы `resolveTableForeignKeys` не возвращал устаревшие display-значения.
4.  **Security Layer (Access Control):** В слое `dbGateway` на уровне `app` реализована автоматическая фильтрация данных для всех операций чтения/обновления/удаления (кроме `admin`):
    - Если в таблице есть `userId`, записи фильтруются по ID текущего пользователя.
    - Если есть `organizationId` или `hotelId`, записи фильтруются по привязке пользователя к организациям (через `user_organizations`).
    - Настройки безопасности (поля и исключения) берутся из `app.config.json`.

| operation | Sequelize метод |
|---|---|
| `read` | `Model.findAll()` |
| `findByPk` | `Model.findByPk()` |
| `findOne` | `Model.findOne()` |
| `count` | `Model.count()` |
| `create` | `Model.create()` |
| `update` | `Model.update()` |
| `delete` | `Model.destroy()` |

### Инициализация
- `drive_root/init.js` → `require('./dbGateway')` (загружает ядро)
- `drive_forms/init.js` → `require('./dbGateway')` (регистрирует forms-middleware)
- Приложения регистрируют app-middleware в своём `server.js` или `init.js` по необходимости

### Что НЕ проходит через dbGateway
Системные операции (сессии, авторизация, миграции) пока используют прямые вызовы Sequelize: `getUserBySessionID`, `createNewUser`, `createGuestUser`, `loadDefaultValuesFromDB`.

### Кэш пользователя сессии + инвалидация (`getUserBySessionID`)
`getUserBySessionID(sessionID)` (drive_root/globalServerContext) кэширует полную plain-запись пользователя в `memory_store` (ns `session_users`): L1 (синхронный Map) → L2 (общий memory_store) → L3 (БД). Запись включает ВСЕ поля, в т.ч. `mustChangePassword`, роль и т.п. **КРИТИЧНО:** если меняешь поле пользователя, влияющее на доступ (роль, `mustChangePassword`), напрямую через Sequelize (минуя dbGateway-инвалидацию), вызови `globalServerContext.invalidateSessionUser(sessionID)` (`= memory_store.del('session_users', sessionID)`) — иначе гейты/RLS продолжат работать по устаревшей копии. Пример: `login.server.js#changePassword` после `user.update({ mustChangePassword:false })` зовёт `invalidateSessionUser`.

### Гейт обязательной смены пароля (forced password change)
Цель — не дать работать в системе в обход обязательной смены пароля. `login()` привязывает сессию к пользователю сразу (сессия аутентифицирована), поэтому одной клиентской формы мало: на refresh десктоп грузится. Защита **серверная**, в двух RPC-чокпойнтах (оба резолвят user из cookie-сессии):
- **`/server-call`** (`drive_root/server.js`, callServer → `loadServerScript`-функции, в т.ч. операции БД через uniForm): если `user.mustChangePassword`, блок `403 PASSWORD_CHANGE_REQUIRED`, КРОМЕ `uid === 'login.actions'` (форма смены + boot).
- **`/app/call` и `/upload`** (`drive_forms/server.js`, callServerMethod → `invokeAppMethod`): блок полностью (`isPasswordChangePending(sessionID)` → `denyPasswordChange(res)`). Приложение логина свои методы зовёт через `/server-call`, не сюда, поэтому форма смены не страдает. `/loadApps` НЕ гейтится (нужно загрузить бандл логина).

Поток: `getBootInfo` возвращает `mustChangePassword` (читает из БД по `ctx.user.UID`); boot (`apps/login/resources/public/client.js`) при `authenticated && mustChangePassword` → `MySpace.open('login', { mode:'changePassword', forced:true })`. Параметр `forced` пробрасывается `MySpace.open → createInstance/onOpen → buildForm`; `buildForm`/`_renderMode` при forced скрывают «старый пароль» (`setHidden`) и делают окно **модальным** (`setModal(true)` — оверлей блокирует десктоп). После смены: `invalidateSessionUser` → `location.reload()` → гейты отпускают → десктоп. (Замечание: при многопроцессном запуске L1-кэш на «чужом» воркере может держать старый флаг; проект — один процесс, `del` чистит L1+L2.)

### `resolveTableForeignKeys` — серверный FK-резолв (globalServerContext.js)

Преобразует сырые FK-значения (UID) в человекочитаемые display-значения для каждой строки данных. Вызывается автоматически внутри `getDynamicTableData` после загрузки строк из БД.

**Алгоритм (батчинг + LRU-кэш):**

```
1. Собрать все FK-поля из metadata (fields.filter(f => f.foreignKey !== null))
2. Для каждого FK-поля собрать уникальные значения UID из всех строк
3. Проверить LRU-кэш (_fkDisplayCache): убрать уже закэшированные UID
4. Для оставшихся — 1 запрос WHERE UID IN (...) на FK-таблицу (параллельно Promise.all)
5. Заполнить кэш из результатов
6. Присвоить __<field>_display каждой строке из кэша
```

**LRU-кэш:**
| Параметр | Значение |
|---|---|
| `_fkDisplayCache` | In-memory `Map`, ключ = `"tableName::UID"` |
| `_FK_CACHE_MAX` | 2000 записей (FIFO-вытеснение) |
| `_FK_CACHE_TTL` | 60 секунд |
| Инвалидация | `invalidateFkCache(tableName)` — вызывается из executor'а dbGateway после create/update/delete |

**Результат оптимизации:** Вместо N×M запросов `findByPk` (по одному на каждую FK-ячейку каждой строки) выполняется максимум K запросов `WHERE UID IN (...)` (K = количество уникальных FK-таблиц), а при повторных загрузках — 0 запросов (всё из кэша).

**Экспорт:**
```javascript
module.exports.resolveTableForeignKeys = resolveTableForeignKeys;
module.exports.invalidateFkCache = function(tableName) { ... };
```

## 7. ПРОЦЕСС МИГРАЦИИ БАЗЫ ДАННЫХ (createDB.js)

### Запуск
`index.js` спавнит `drive_root/db/createDB.js` как дочерний процесс. Весь вывод миграции идёт от дочернего процесса. Основной сервер стартует только после успешного завершения дочернего.

### Цепочка инициализации
```
1. collectAllModels()          → сырые JSON-дефиниции из всех источников (без UID)
2. mergeModelDefinitions()     → слияние дефиниций с разных уровней
3. triggerProjectEvent('onModelsPostCollect', { mergedModelsDef, ... })
   ├── node_modules/my-old-space/events_handler.js → onModelsPostCollect  (framework)
   └── ./events_handler.js (проект)                → onModelsPostCollect  (project)
      ← ЗДЕСЬ ИНЪЕКТИРУЕТСЯ UID в каждую def.fields перед sequelize.define
4. computeCreateOrder()        → топологическая сортировка по FK
5. sequelize.define() для каждой модели
6. Model.sync({ alter: true }) → DDL
7. Начальный сид defaultValues
8. triggerProjectEvent('onDatabasePostInit', { sequelize })
```

### triggerProjectEvent — порядок вызова обработчиков
```javascript
// Расположение в createDB.js:
const frameworkHandlerPath = path.resolve(__dirname, '../../events_handler.js');
// => node_modules/my-old-space/events_handler.js  (НЕ drive_root/events_handler.js!)

const projectHandlerPath = path.join(projectRoot, 'events_handler.js');
// => D:/prj/wonunger/events_handler.js
```
Сначала вызывается framework-обработчик, затем project-обработчик. Оба получают один и тот же объект `context` — мутации видны следующему обработчику.

**КРИТИЧНО:** project `events_handler.js` загружается через `require()` (CommonJS). Поэтому он ДОЛЖЕН экспортировать через `module.exports`, а не `export default` (ESM). Неверный синтаксис приводит к тому, что файл не загружается, `onModelsPostCollect` не вызывается и UID не инъектируется.

### Инъекция UID (onModelsPostCollect)
`collectAllModelDefs()` возвращает **сырые JSON-дефиниции без поля UID** — поле UID отсутствует в `db.json` специально (см. инструкции). Его необходимо вставить до `sequelize.define()`. Паттерн из project `events_handler.js`:
```javascript
for (const def of mergedModelsDef) {
    if (!def.fields) def.fields = {};
    // Убрать primaryKey у других полей
    for (const [name, fld] of Object.entries(def.fields)) {
        if (name !== 'UID' && fld && fld.primaryKey) delete fld.primaryKey;
    }
    // Добавить/нормализовать UID
    if (!def.fields.UID) {
        def.fields.UID = { type: "STRING", allowNull: false, primaryKey: true, defaultValue: "GENERATE_UID" };
    } else {
        Object.assign(def.fields.UID, { primaryKey: true, allowNull: false, type: "STRING" });
        if (!def.fields.UID.defaultValue) def.fields.UID.defaultValue = "GENERATE_UID";
    }
}
```

### Инъекция реквизита `number` + автонумерация (сущности)
Любая **сущность** (`entityConfig.entityType` ∈ `document` / `directory` / `catalog` / `справочник`) системно — по аналогии с UID — получает строковый реквизит `number` и автонумерацию на нём. Прикладному коду объявлять их не нужно.

- **Логика** — `drive_root/db/entityNumber.js`: `injectEntityNumber(def)` добавляет поле `number` (если его нет) и хук `default.autoNumber` с `params.field='number'` в `entityConfig.hooks.beforeCreate` (если ещё не назначен). Идемпотентно. **Ручной ввод номера сохраняется** (см. `default.autoNumber`). `isEntityDef(def)` определяет сущность по `entityType`.
- **Две точки вызова** (как у UID — миграция + рантайм):
  - **Миграция:** корневой `node_modules/my-old-space/events_handler.js#onModelsPostCollect` (теперь существует; `triggerProjectEvent` вызывает его ПЕРВЫМ) → создаёт колонку `number`.
  - **Рантайм:** `globalServerContext.collectAllModelDefs()` (перед `return`) — **единый источник** определений и для построения моделей, и для `_cachedModelDefs` (подписи в `getTableMetadata`). `require`-кэш отдаёт одни и те же объекты, поэтому мутация видна всем потребителям.
- **Гочча (CRITICAL):** `getTableMetadata` берёт подпись поля из `_cachedModelDefs` (db.json-дефиниции), а НЕ из `Model.rawAttributes`. Поэтому инжектить поле нужно именно в `collectAllModelDefs` (источник `_cachedModelDefs`) — иначе авто-колонка в списке получит подпись = имя поля. Подпись `number` = `{ i18n: 'number_field' }`; подпись представления `name` = `{ i18n: 'name_field' }` (ключи в `drive_forms/i18n.json`).
- **Поле `name` сущности** — это «представление», заполняется не автонумерацией, а билдером через `applyPresentation` (см. раздел 21).

### computeCreateOrder — топологическая сортировка (алгоритм Кана)
Порядок создания таблиц вычисляется из FK-зависимостей. Два важных краевых случая:
- **Само-референция** (`FileSystem_Files.parentId → FileSystem_Files`): ребро пропускается (`referenced !== table`), иначе indegree никогда не падает до нуля.
- **Дублирующиеся FK на одну таблицу** (напр. `ownerId` + `userId` → `users`): ребро считается только один раз через `Set countedEdges`, иначе indegree завышен и таблица застревает в очереди.

| `quantity` | DECIMAL | Количество (ночи, штуки, …) |
| `unitPrice` | DECIMAL | Цена за единицу (снапшот) |
| `taxRate` | DECIMAL | Ставка налога (снапшот) |
| `amount` | DECIMAL | Итого по строке (quantity × unitPrice × (1+taxRate)) |

### 9.7 Паттерн `defaultValues.json`

Для предопределённых системных записей (с фиксированными UID) используется файл `apps/<app>/db/defaultValues.json`. В проекте используется `apps/common/db/defaultValues.json` (guest_types).

- Файл сканируется патчем в `node_modules/my-old-space/drive_root/db/createDB.js` при старте приложения.
- Записи вставляются только если их `UID` ещё нет в таблице (`findOrCreate`).
- Lookup в коде: `getDefaultValue(level, tableName, defaultValueId)`.
- Формат: объект, где ключ = имя таблицы (`"guest_types"`), значение = массив записей с полем `UID`.
- **Досев на СУЩЕСТВУЮЩУЮ БД (важно):** секция 6 `createDB.js` («Update/cleanup default values») выполняется при КАЖДОМ старте, не только на свежей установке: новые записи (новый `UID`) создаются, существующие — обновляются по перечисленным полям, а записи уровня, исчезнувшие из `defaultValues.json`, **удаляются** из основной таблицы. Поэтому добавить новый язык/перевод/справочную запись = просто дописать строку в `defaultValues.json` + рестарт (НЕ нужно пересоздавать БД). Обратная сторона: удалив строку, удаляешь и запись из БД.

### 9.9 Настройки автозаполнения пользователя (`UserSettingsDefaults`)

**Файл:** `apps/UserSettings/db/db.json`

**Формат данных для таблицы автозаполнения** (в `loadAutofill`):
- `r.__tableName_display = r.tableLabel || r.tableName`
- `r.__recordId_display = r.recordLabel || r.recordId`

Без этих `__display`-полей recordSelector-колонки покажут сырые ID вместо человекочитаемых названий.

### `__display`-поля — паттерн для FK/recordSelector колонок в таблицах

В таблицах с `inputType: 'recordSelector'`, если строка данных содержит `__<fieldName>_display`, это значение показывается как текст ячейки. При сохранении — оно же записывается в лейбл-поле (`tableLabel`, `recordLabel` и т.д.).

Паттерн используется повсюду: `data_updateParentArray(dataKey, rowIndex, colDef, newVal, displayVal)` автоматически сохраняет `displayVal` в `parentArr[rowIndex]['__' + colDef.data + '_display']`.

### `user_settings_table_list` — виртуальная таблица списка таблиц

**Регистрация:** В `apps/UserSettings/init.js` регистрируется дважды:
1. Как **record**-лейаут (для `{ tableName: 'user_settings_table_list', recordID }`)
2. Как **list**-лейаут (для `{ dbTable: 'user_settings_table_list' }`) — это открывается через recordSelector

Обе регистрации используют один и тот же `tableListLayout` и `onLoadData_tableList`.

**`onLoadData_tableList`** — формирует список всех доступных таблиц из `collectAllModelDefs()`. Дедупликация по `tableName` через `Set` обязательна — `collectAllModelDefs()` загружает из нескольких db.json и может возвращать дубли.

**`collectAllModelDefs()` и дубли:** Функция загружает `db.json` из `drive_root/db/`, `drive_forms/db/` и `apps/*/db/`. Одна таблица может быть определена в нескольких файлах (разные уровни). Любой код, формирующий UI-список таблиц, ОБЯЗАН дедуплицировать результат.

## 10. КАСТОМНЫЕ ЛЕЙАУТЫ ФОРМ (layoutMemory)

### Назначение

Модуль `drive_root/layoutMemory.js` позволяет хранить на сервере произвольные JSON-лейауты для `uniForm`. Перед генерацией стандартного лейаута `uniForm` проверяет, не загружен ли в память подходящий кастомный лейаут.

Матч считается успешным, если совпадают: **appName + tableName + роль пользователя** (поддерживается wildcard `'*'` — любая роль).

### API

```javascript
const layoutMemory = require('node_modules/my-old-space/drive_root/layoutMemory');
// или relative path от сервера приложения:
// require('../../drive_root/layoutMemory')

// Сохранить лейаут
await layoutMemory.saveLayout({
    appName: 'uniForm',   // только 'uniForm'
    tableName: 'hotels',         // имя таблицы
    roles: ['admin', 'manager'], // роль или массив ролей; '*' = любая роль
    layout: [ /* JSON-лейаут */ ],
    clientScript: clientUID,     // UID клиентского скрипта (из loadScript)
    formIcon: '/apps/general_icons/resources/public/16x16/document.png', // иконка ЗАПИСИ. Можно НЕ задавать — фреймворк подставит по entityType (document → document, list → journal)
    listIcon: '/apps/general_icons/resources/public/16x16/journal.png',  // иконка СПИСКА (опц., отлична от иконки записи)
    appCaption:    { i18n: 'bookings_app_caption' }, // заголовок СПИСКА (мн. число); строка ИЛИ { i18n: 'key' }
    recordCaption: { i18n: 'Booking' },              // заголовок ЗАПИСИ (ед. число); к нему добавляется представление (name)
    events: { /* onBeforeSave и др. */ }
});

// Получить лейаут для конкретной роли (null если не найден)
const layout = await layoutMemory.getLayoutForUser('uniForm', 'hotels', 'admin');

// Иконки/заголовки по имени таблицы (null если не зарегистрированы)
const icon       = layoutMemory.getTableIcon('bookings');          // иконка записи (formIcon)
const listIcon   = layoutMemory.getTableListIcon('bookings');      // иконка списка (listIcon)
const recCaption = layoutMemory.getTableRecordCaption('bookings'); // заголовок записи, ед. число (recordCaption)

// Вспомогательная функция: получить роль пользователя по session ID
const role = await layoutMemory.getUserRoleBySession(sessionID);
```

### Приоритет

1. Точное совпадение роли (`{appName}|{tableName}|{userRole}`)
2. Wildcard `*` (`{appName}|{tableName}|*`)
3. Стандартный auto-generated лейаут

### Хранилище

Использует `drive_root/memory_store.js`, namespace `'layouts'`, ключ = `{appName}|{tableName}|{role}`. Данные живут в памяти процесса (и опционально в Redis/сервисе) до перезапуска, если не записаны явно снова.

### Где вызывать saveLayout

Функция доступна из любого серверного модуля проекта. Типичные места вызова:
- `apps/<appName>/init.js` (PROJECT, рекомендуемое место) — загружается фреймворком автоматически
- `events_handler.js` (хук `onDatabasePostInit`) — загрузка при старте сервера
- `server.js` любого приложения — в ответ на RPC-действие пользователя

### Паттерн: init.js в приложении проекта

Фреймворк (`drive_forms/init.js`) автоматически сканирует все зарегистрированные приложения и вызывает их `init.js` при старте, если він существует. Сигнатура: `module.exports = async function(modelsDB) { ... }`.

Для организации кастомных лейаутов создай файл `apps/<appName>/init.js` в корне **проекта** (не `node_modules`):

```javascript
// apps/organizations/init.js
'use strict';
module.exports = async function (modelsDB) {
    const layoutMemory = require('../../node_modules/my-old-space/drive_root/layoutMemory');
    await layoutMemory.saveLayout({
        appName: 'uniForm',
        tableName: 'bookings',
        roles: 'user',
        layout: [ /* ... */ ],
        formIcon: '/apps/booking_icons/resources/public/16x16/booking_status.png',
        appCaption: { i18n: 'bookings_app_caption' },
    });
};
```

### Кастомный лейаут vs автогенерация — разграничение ответственности

**CRITICAL:** Табличные части (`tabularSection`) — часть **автоматически генерируемого** лейаута в `generateFormSpec`. Они строятся **внутри** блока `if (!layout)` вместе с остальными контролами из метаданных модели. Они НЕ добавляются поверх кастомного лейаута.

- **Кастомный лейаут (из `layoutMemory`):** автор лейаута полностью контролирует форму. Если нужны табличные части — их надо описать в кастомном лейауте явно.
- **Автогенерированный лейаут:** строится из метаданных модели (`buildTableFieldsFromModel`) + табличные части из `getTabularSectionsForTable` — всё в одном блоке.
- **Форма ЗАПИСИ (авто):** `[{ type:'commandBar' }, { type:'group', orientation:'vertical', alignFields:true, noBorder:true, layout: controls }]`. Поле `UID` отфильтровано из `controls` (`f.name !== 'UID'`), но остаётся в `data` (нужен для pre-gen нового UID и сохранения). Группа без `caption` и с `noBorder:true` — без видимой рамки и сырого ярлыка-имени таблицы (имя записи в заголовке окна).
- **Форма СПИСКА (авто):** `{ type:'table', properties:{ dynamicTable:true, ... } }`. Колонка `UID` скрывается в единой точке прохода колонок `dynamicTableRegistry.getDynamicTableData` (после `fields = raw.fields || fieldConfig`) — покрывает и модельные `raw.fields` (из `globalServerContext.getDynamicTableData`), и `fieldConfig` (из `buildTableFields`). Идентичность строки — из `row.UID`, не из колонки.

### Инвариант хранения (CRITICAL — защита от мутации кэша)

`memory_store` (L1) хранит объекты **по ссылке** в in-process `Map`. Если получить объект через `getSync` и затем мутировать его (`splice`, `push`, изменение поля), **закэшированный оригинал тоже изменится**.

**Правило:** При получении кастомного лейаута из `layoutMemory` всегда делай глубокий клон перед использованием:

```javascript
layout = JSON.parse(JSON.stringify(customLayout));
```

Без клона каждое последующее открытие формы будет накапливать изменения в кэше (например, дублировать группы).

```javascript

            {
                type: 'group', caption: 'Отель', orientation: 'vertical',

                    { type: 'textbox', name: 'name', data: 'name', caption: 'Название' },
                    { type: 'recordSelector', name: 'organizationId', data: 'organizationId', caption: 'Организация',
                      properties: { showSelectionButton: true, selection: { table: 'organizations', idField: 'UID', displayField: 'name' } } }
```

## 11. КЭШИРОВАНИЕ ЧЕРЕЗ memory_store

### Концепция

`drive_root/memory_store.js` — общий сервер памяти для всех воркер-процессов. Используется для кэширования данных, которые дорого получать из БД при каждом запросе.

**Уровни кэша:**
| Уровень | Хранилище | Скорость | Область видимости |
|---|---|---|---|
| L1 | In-process `Map` | Мгновенно (0 IO) | Один воркер |
| L2 | HTTP-сервис (порт 40001) | ~1 мс | Все воркеры одного сервера |
| L3 | БД (Sequelize) | ~10–50 мс | Постоянное хранилище |

**API:**
```javascript
const memoryStore = require('./memory_store');

// Синхронно (только L1 — in-process Map)
const val = memoryStore.getSync('namespace', 'key');   // null если нет
const hit = memoryStore.hasSync('namespace', 'key');   // boolean

// Асинхронно (L1 → L2)
const val = await memoryStore.get('namespace', 'key'); // null если нет

// Запись (L1 + L2)
await memoryStore.set('namespace', 'key', value);
```

### Встроенное кэширование в базовых функциях

Кэширование должно находиться **в самих функциях**, а не в вызывающем коде. Не создавай отдельные прослойки кэша снаружи уже закэшированных функций.

| Функция | Файл | Namespace | Ключ | Что кэшируется |
|---|---|---|---|---|
| `getUserBySessionID(sessionID)` | `drive_root/globalServerContext.js` | `session_users` | `sessionID` | Объект пользователя `user.get({ plain: true })` |
| `getUserAccessRole(user)` | `drive_forms/globalServerContext.js` | `user_roles` | `user.UID` | Строка с именем роли |

**Паттерн (L1 → L2 → L3):**
```javascript
// L1
const hit = _memoryStore.getSync(NS, key);
if (hit !== null && hit !== undefined) return hit;
// L2
const hit2 = await _memoryStore.get(NS, key);
if (hit2 !== null && hit2 !== undefined) return hit2;
// L3: DB-запрос
const result = /* ... */;
await _memoryStore.set(NS, key, result);
return result;
```

### Invalidation

При логауте пользователя необходимо инвалидировать ключи `session_users` / `user_roles` через `memoryStore.del` (если метод реализован), иначе данные устаревают до перезапуска сервера. При изменении роли — инвалидировать `user_roles` для данного `user.UID`.

## 12. ХРАНИЛИЩЕ КЛИЕНТСКИХ ФАЙЛОВ (fileStore)

### Назначение

`drive_root/fileStore.js` — хранилище текстовых клиентских файлов (скрипты, HTML и пр.) в `memory_store`, с контролем доступа по роли пользователя.

Файлы хранятся **только в памяти** (namespace `client_files`). Загружаются при старте сервера (обычно из `apps/<app>/init.js`) и живут до перезапуска.

### API (серверная сторона)

```javascript
const { loadFile, loadScript, getFile } = require('node_modules/my-old-space');
// или напрямую:
const fileStore = require('node_modules/my-old-space/drive_root/fileStore');
```

| Функция | Сигнатура | Назначение |
|---|---|---|
| `loadFile` | `(text, role, fileType) → Promise<uid>` | Сохранить файл. Для `'js'` — прогоняет через `optimizeJS` и `translateText`. Возвращает UID. |
| `loadScript` | `(text, role) → Promise<uid>` | Обёртка над `loadFile` с `fileType = 'js'` |
| `getFile` | `(uid, userRole) → { text, fileType } \| null` | Получить файл по UID с проверкой роли. Синхронный (L1 only). |

**Параметр `role`** — строка с именем роли, которой достаточно для доступа к файлу. `'admin'` имеет доступ к любому файлу вне зависимости от `role`.

**Параметр `userRole`** в `getFile` — строка **или массив строк** (пользователь может иметь несколько ролей). Список ролей не захардкожен в фреймворке и не имеет иерархии: доступ разрешён при точном совпадении одной из ролей с требуемой.

### Обработка JS-скриптов при загрузке

`optimizeJS(text)` — минификация:
- Удаляет блочные `/* */` и строчные `//` комментарии
- Схлопывает пробелы/переносы строк в один пробел
- Убирает пробелы вокруг знаков пунктуации и операторов
- Результат — однострочный нечитаемый JS

`translateText(text, language)` — **TODO**, пока заглушка, возвращает текст без изменений.

### HTTP-эндпоинт

`GET /files/:uid` — отдаёт файл клиенту. Реализован в `drive_root/server.js`.

- Извлекает `sessionID` из cookie
- Получает роль пользователя через `getUserBySessionID` + `getUserAccessRole`
- Если пользователь не авторизован — считает роль `'public'`
- Вызывает `getFile(uid, userRole)`; при отказе → `403`
- `Content-Type` определяется по `fileType` файла (`js` → `application/javascript`, `css` → `text/css`, и т.д.)

### Паттерн action `runScript` в лейауте (клиентская сторона)

> **Устаревший способ.** Для новых кнопок предпочтительнее использовать `events: { onClick: ... }` (см. ниже «Декларативные события `events`»). `action: 'runScript'` продолжает работать для обратной совместимости.

`DataForm.doAction('runScript', { uid, fn })` реализован в `UI_classes.js`:
1. `fetch('/files/' + uid)` — загружает код с сервера (с проверкой роли)
2. `new Function(code)()` — исполняет код; скрипт **обязан вернуть объект** с функциями через `return { ... }`
3. Вызывает `mod[fn]()` — именованную функцию из объекта

Оба параметра `uid` и `fn` обязательны — без них `showAlert` сообщит об ошибке.

**Структура скрипта:**
```javascript
function doSomething(ev, ctx) {
    // ctx.form — ссылка на DataForm
    // ctx.fnParams — параметры из лейаута (с резолвленными {data.field})
    showAlert('Привет!');
}
function doOther() {
    showAlert('Пока!');
}
return { doSomething, doOther };
```

**Кнопка в JSON-лейауте (устаревший способ):**
```json
{ "type": "button", "action": "runScript", "caption": "Кнопка",
  "params": { "uid": "<uid от loadScript>", "fn": "doSomething" } }
```

### Декларативные события `events` на элементах лейаута

Любой элемент лейаута, имеющий `name`, может декларировать обработчики событий.
`clientScript` (UID скрипта) задаётся один раз в `saveLayout` — все events наследуют его.

**Три формата привязки:**

| Формат | Пример | Когда использовать |
|---|---|---|
| Строка (имя функции) | `'onRoomActivated'` | Простой обработчик без параметров |
| Объект с `fn` | `{ fn: 'sayHello', fnParams: { name: 'Вася' } }` | Нужны fnParams или свой clientScript |
| Полный объект | `{ clientScript: uid, fn: 'handler' }` | Другой скрипт (не из saveLayout) |

**Сигнатура функции-обработчика:**
```javascript
function myHandler(eventArg1, eventArg2, ..., ctx) {
    // Последний аргумент ctx — всегда контекст:
    // ctx.form     — DataForm (controlsMap, _dataMap, doAction, ...)
    // ctx.fnParams — резолвленные параметры (с {data.field} → значение)
}
```

**Пример лейаута:**
```javascript
await layoutMemory.saveLayout({
    appName: 'uniForm',
    tableName: 'bookings',
    roles: 'user',
    clientScript: clientUID,       // ← дефолтный скрипт для всех events
    layout: [
        // Кнопка с обработчиком onClick
        { type: 'button', name: 'btnHello', caption: 'Привет',
          events: { onClick: { fn: 'sayHello', fnParams: { name: 'Вася' } } } },

        // Кнопка — строковый shorthand (без fnParams)
        { type: 'button', name: 'btnGreet', caption: 'Приветствие',
          events: { onClick: 'greet' } },

        // Таблица с обработчиком onRowActivate
        { type: 'table', name: 'ts_rooms', data: 'booking_rooms',
          events: { onRowActivate: 'onRoomActivated' } },

        // Top-level синтаксис (без вложенного events:)
        { type: 'button', name: 'btnAlt', caption: 'Альтернатива',
          onClick: 'altHandler' },
        
        // Стандартные кнопки — без изменений
        { type: 'button', action: 'save',   caption: 'Сохранить' },
        { type: 'button', action: 'cancel', caption: 'Отмена' },
    ]
});
```

**Поддерживаемые события:**

| Категория | Имена | Источник |
|---|---|---|
| DOM-события | `onClick`, `onDoubleClick`, `onMouseOver`, `onKeyDown`, `onFocus`, `onBlur`, ... | `addEventListener` на `element` |
| Объектные колбэки | `onRowActivate`, `onSelect`, `onChange`, `onAction`, ... | Свойство объекта `ctrl[eventName]` |
| ResizeObserver | `onResize` | `ResizeObserver` на `element` |

**Цепочка:** Если на контроле уже есть обработчик (напр. `masterFor` установил `onRowActivate`), новый обработчик цепляется **поверх** — оба срабатывают.

**`{data.field}` в `fnParams`:** Резолвится автоматически из `_dataMap` формы перед вызовом. Работает рекурсивно.

**Определение DOM vs объектный:** Если контрол уже имеет свойство `onClick` (как Button), событие обрабатывается как объектный колбэк, а не через `addEventListener` — избегая двойного срабатывания.

### Типичный сценарий использования

```javascript
// apps/myApp/init.js
'use strict';
module.exports = async function (modelsDB) {
    const { loadScript } = require('../../node_modules/my-old-space');
    const layoutMemory  = require('../../node_modules/my-old-space/drive_root/layoutMemory');

    const scriptUID = await loadScript(`
        function greet() { showAlert('Привет из FileStore!'); }
        return { greet };
    `, 'user');

    await layoutMemory.saveLayout({
        appName: 'uniForm', tableName: 'orders', roles: 'user',
        layout: [
            // ... поля ...
            { type: 'group', caption: '', orientation: 'horizontal', layout: [
                { type: 'button', action: 'save',      caption: 'Сохранить' },
                { type: 'button', action: 'cancel',    caption: 'Отмена' },
                { type: 'button', action: 'runScript', caption: 'Привет',
                  params: { uid: scriptUID, fn: 'greet' } }
            ]}
        ]
    });
};
```

> UID генерируется динамически при каждом старте сервера. Чтобы увидеть его — добавь `console.log(scriptUID)` в `init.js` и открой `http://localhost:3000/files/<uid>` в браузере.

## 13. ХРАНИЛИЩЕ СЕРВЕРНЫХ СКРИПТОВ (serverScriptStore)

### Назначение

`drive_root/serverScriptStore.js` — хранилище серверных объектов с функциями, вызываемых с клиента. Функции имеют полный доступ к БД, сессии, любым серверным Node.js-модулю.

### Почему in-process Map, а не memoryStore

Функции нельзя сериализовать в JSON — поэтому они не могут быть положены в L2 (HTTP-сервис memoryStore). Объекты живут только в памяти процесса.

Проблемы с несколькими воркерами нет, потому что каждый воркер при старте выполняет `init.js` и регистрирует скрипты самостоятельно. Запрос на `/server-call` попадёт на любой воркер — у каждого уже зарегистрирована нужная функция.

**КРИТИЧНО:** регистрация обязательно должна происходить в `init.js` при старте, а не динамически в рантайме по запросу пользователя — иначе один воркер зарегистрирует, а другой не найдёт скрипт.

### API (серверная сторона)

```javascript
const { loadServerScript, getServerScript } = require('node_modules/my-old-space');
// или напрямую:
const serverScriptStore = require('node_modules/my-old-space/drive_root/serverScriptStore');
```

| Функция | Сигнатура | Назначение |
|---|---|---|
| `loadServerScript` | `(name, scriptObj, role) → name` | Зарегистрировать объект с функциями. Возвращает `name` обратно. |
| `getServerScript` | `(name, userRole) → { scriptObj } \| null` | Получить скрипт с проверкой роли. |

**`name`** — явный стабильный ключ. Рекомендуемая конвенция: `'<приложение>.<группаФункций>'` (например `'organizations.bookingActions'`).

**`role`** — строка или массив, аналогично `fileStore`.

**`scriptObj`** — обычный JS-объект. Каждая функция получает `(params, ctx)` где `ctx = { sessionID, user, role }`.

### HTTP-эндпоинт

`POST /server-call` — вызов серверной функции. Реализован в `drive_root/server.js`.

**Тело запроса:** `{ uid, fn, fnParams }`
- `uid` — имя скрипта (`loadServerScript name`)
- `fn` — имя функции внутри скрипта
- `fnParams` — любой JSON-сериализуемый объект

**Тело ответа:** `{ result }` — возвращаемое функцией значение (null если `undefined`).

- Извлекает `sessionID` из cookie
- Получает `user` и `role` через `getUserBySessionID` + `getUserAccessRole`
- Вызывает `getServerScript(uid, userRole)`; при отказе → `403`
- Вызывает `scriptObj[fn](fnParams, { sessionID, user, role })`

### Глобальный хелпер `callServer` (клиентская сторона)

`window.callServer(uid, fn, fnParams)` — доступен глобально в любом клиентском скрипте (`loadScript`). Делает `POST /server-call`, возвращает `Promise<result>`. При ошибке — бросает `Error`.

### Паттерн использования — вся логика формы в одном файле

Кнопка вызывает клиентскую функцию через `runScript`, клиентская функция вызывает сервер через `callServer`. Никакого специального action `callServer` в лейауте нет.

```javascript
// apps/myApp/init.js
'use strict';
module.exports = async function (modelsDB) {
    const { loadScript, loadServerScript } = require('../../node_modules/my-old-space');
    const layoutMemory = require('../../node_modules/my-old-space/drive_root/layoutMemory');

    // 1. Серверный скрипт — чистый JS-объект с async-функциями
    const serverScriptName = loadServerScript('myApp.actions', {

        async getStatus({ id } = {}, ctx) {
            const record = await modelsDB.MyTable.findByPk(id, { raw: true });
            if (!record) return { error: 'Не найдено' };
            return { status: record.status, name: record.name };
        },

    }, 'user');

    // 2. Клиентский скрипт — знает о серверном через интерполяцию serverScriptName
    const clientUID = await loadScript(`
        async function showStatus({ id } = {}) {
            const result = await callServer('${serverScriptName}', 'getStatus', { id });
            if (result.error) { showAlert('Ошибка: ' + result.error); return; }
            showAlert(result.name + ': ' + result.status);
        }
        return { showStatus };
    `, 'user');

    // 3. Лейаут — кнопка вызывает клиентскую функцию, {data.UID} подставляется из формы
    await layoutMemory.saveLayout({
        appName: 'uniForm', tableName: 'myTable', roles: 'user',
        layout: [
            // ... поля ...
            { type: 'group', caption: '', orientation: 'horizontal', layout: [
                { type: 'button', action: 'save',      caption: 'Сохранить' },
                { type: 'button', action: 'cancel',    caption: 'Отмена' },
                { type: 'button', action: 'runScript', caption: 'Статус',
                  params: { uid: clientUID, fn: 'showStatus', fnParams: { id: '{data.UID}' } } }
            ]}
        ]
    });
};
```

### Резолвинг `{data.fieldName}` в `fnParams`

При вызове `runScript` фреймворк автоматически заменяет строки вида `{data.UID}` значением соответствующего поля из `_dataMap` формы. Работает рекурсивно в объектах и массивах.

```javascript
fnParams: { id: '{data.UID}', hotel: '{data.hotelId}' }
// → перед вызовом функции заменяется на:
fnParams: { id: 'abc123', hotel: 'xyz456' }
```

### Маршрутизация
Статические файлы приложений раздаются по URL-паттерну:
```

```

### Приоритет поиска
1. **Проектный** `apps/` (CWD): `<projectDir>/apps/<appName>/resources/public/<path>`
2. **Пакетный** `apps/` (node_modules): `<packageDir>/apps/<appName>/resources/public/<path>`

## 17. СЕРВЕРНЫЕ СОБЫТИЯ (dispatchServerEvent / onBeforeSave)

### dispatchServerEvent (uniForm/server.js)
Позволяет прикладному коду перехватывать серверные события формы.

**Регистрация обработчика** (в `init.js` проекта):
```javascript
loadServerScript('org.events', {
    onBeforeSave: async function(payload, ctx) {
        // payload: { tableName, record, changes, tabularSections, parentUID, isNew }
        // ctx: { sessionID }
        // Можно мутировать payload.changes
    }
}, 'user');
```

### onBeforeSave — порядок вызова (CRITICAL)
`dispatchServerEvent('onBeforeSave', ...)` вызывается **ДО** операции create/update в `applyChanges`. Это позволяет:
- Заполнить обязательные поля, скрытые от пользователя (например, `organizationId` из профиля)
- Провалидировать данные перед записью

**Payload:**
| Поле | Значение |
|---|---|
| `tableName` | Имя таблицы |
| `record` | `null` (запись ещё не создана/не загружена на этом этапе) |
| `changes` | Объект с изменениями — **мутабельный**, изменения подхватятся при create/update |
| `tabularSections` | Данные табличных частей |
| `parentUID` | UID родительской записи |
| `isNew` | `true` если запись новая (create), `false` если update |

### Санитизация числовых полей ТЧ
В `uniForm/server.js` перед INSERT строки ТЧ выполняется проверка: если значение поля — пустая строка `""` и тип поля — числовой (INTEGER, FLOAT, DECIMAL, DOUBLE, REAL), значение заменяется на `defaultValue` из схемы или `null`. Это предотвращает ошибку PostgreSQL «неверный синтаксис для типа integer: ""».

## 18. НАСТРОЙКИ ПОЛЬЗОВАТЕЛЯ (UserSettings — EAV-модель)

UserSettings использует архитектуру **Entity-Attribute-Value** (EAV). Реальной таблицы `user_settings` в БД нет.

### Схема таблиц

| Таблица | Назначение |
|---|---|
| `UserSettingsTypes` | Типы значений: string, number, boolean, date, enum |
| `UserSettingsFields` | Поля настроек (name, displayName, typeId → UserSettingsTypes, options JSON) |
| `UserSettingsStringValues` | Значения строковых полей (userId, settingsFieldId, value STRING) |
| `UserSettingsNumberValues` | Значения числовых полей (value INTEGER) |
| `UserSettingsBooleanValues` | Значения булевых полей (value BOOLEAN) |
| `UserSettingsDateValues` | Значения полей дат (value DATE) |
| `Languages` | Справочник языков (name, code). Ссылочное поле из UserSettings |

Каждая таблица значений имеет уникальный индекс `(userId, settingsFieldId)` — одно значение на пользователя на поле.

### Ссылочные поля (referenceTable)

Поле `options` в `UserSettingsFields` поддерживает два формата:
- **Массив** (для enum): `["Classic", "Dark", "Blue"]` → контрол `emunList`
- **Объект с referenceTable** (для ссылок): `{ "referenceTable": "languages", "displayField": "name" }` → контрол `recordSelector`

Значение ссылочного поля хранится как UID в `UserSettingsStringValues` (typeId = string).

### Цепочка загрузки данных

1. `client.js` → `MySpace.open('uniForm', { tableName: 'user_settings' })`
2. `uniForm/server.js generateFormSpec()` → находит кастомный лейаут в `layoutMemory` → видит событие `onLoadData` → вызывает серверный скрипт
3. `init.js onLoadData()` → вызывает `server.js getSettings()` → загружает поля из `UserSettingsFields`, значения из таблиц по типу, резолвит `referenceDisplay` для ссылочных полей
4. Данные возвращаются как `[{ name, value, tabularSection, selection? }]` → форма отрисовывается

### Цепочка сохранения

1. Клиент: `form.collectData()` → `callServer(serverScriptName, 'onSave', { changes, tableName })`
2. `init.js onSave()` → вызывает `server.js saveSettings()` → upsert в соответствующую таблицу значений по типу поля

### Повторное открытие формы

`UserSettings` имеет `allowMultipleInstances: false`. После закрытия `uniForm` экземпляр `UserSettings` остаётся в `MySpace.instances`. При повторном открытии вызывается `onOpen()`, который заново открывает `uniForm`.

## 19. АРХИТЕКТУРНЫЙ ПАТТЕРН: РАЗДЕЛЕНИЕ ФОРМ ПО ФАЙЛАМ

### Назначение

Новый способ организации кода приложений. Используется в `apps/booking/` (новая версия) в противовес монолитному `init.js` из `apps/booking_old/`.

Цель — разделить форму на три независимых артефакта:
- **JSON-лейаут** — описание полей, таблиц, кнопок (без кода)
- **Серверный модуль** — бизнес-логика (RPC-функции, onBeforeSave)
- **Клиентский файл** — UI-логика (реакция на кнопки, заполнение ТЧ)

`init.js` становится минимальной «склейкой» (~25 строк).

### Структура директории приложения

```
apps/<appName>/
├── init.js                        # Только склейка: loadServerScript + loadScript + saveLayout
├── i18n.json                      # Переводы для tForSession()
├── db/
│   ├── db.json                    # Схема БД (без UID — инъектируется фреймворком)
│   └── defaultValues.json         # Предопределённые записи (опционально)
└── forms/
    ├── <tableName>.layout.json    # Чистый JSON-массив лейаута формы
    ├── <tableName>.server.js      # Модуль-фабрика серверных функций
    └── <tableName>.client.js      # Клиентский JS с плейсхолдером __SERVER_SCRIPT__
```

### `<tableName>.layout.json` — чистый JSON-лейаут

Обычный JSON-массив, описывающий форму. Никакого JS-кода. Обработчики событий — строковые имена функций:

```json
[
  { "type": "group", "caption": "Основное", "orientation": "horizontal", "layout": [
    { "type": "field", "label": "Клиент", "data": "clientId", "showSelectionButton": true,
      "selectionTable": "clients", "icon": "..." }
  ]},
  { "type": "group", "caption": "", "orientation": "horizontal", "layout": [
    { "type": "button", "action": "save", "caption": "Сохранить", "icon": "..." },
    { "type": "button", "name": "btnCalc", "caption": "Рассчитать", "icon": "...",
      "events": { "onClick": "calculateCost" } }
  ]}
]
```

Строковый shorthand `"onClick": "calculateCost"` — функция из `clientScript`, зарегистрированного в `saveLayout`.

### `<tableName>.server.js` — модуль-фабрика

Экспортирует функцию-фабрику, получающую `modelsDB` и `Utilities` от `init.js`.
Это позволяет избежать глобального require Sequelize-моделей.

```javascript
'use strict';
const { tForSession } = require('../../../node_modules/my-old-space/drive_forms/globalServerContext');

module.exports = function (modelsDB, Utilities) {
    return {
        async onBeforeSave({ record, changes, tabularSections }, ctx) {
            // Вызывается ДО записи в БД. Мутируй changes для передачи значений.
        },

        async getStatus({ id } = {}, ctx) {
            if (!id) return { error: await tForSession('id required', ctx.sessionID) };
            const rec = await modelsDB.MyTable.findByPk(id, { raw: true });
            if (!rec) return { error: await tForSession('Not found', ctx.sessionID) };
            return { name: rec.name, status: rec.status };
        },
    };
};
```

### `<tableName>.client.js` — клиентский JS с плейсхолдером

Обычный `.js` файл (не модуль). Конец файла — `return { fn1, fn2, ... }` (требование `loadScript`).
Плейсхолдер `__SERVER_SCRIPT__` заменяется в `init.js` при загрузке.

```javascript
// Клиентские функции формы <tableName>.

function sayHello(ev, ctx) {
    showAlert('Привет, ' + (ctx.fnParams && ctx.fnParams.name || 'гость') + '!');
}

async function calculateCost(ev, ctx) {
    var form = ctx.form;
    var bookingId = form._dataMap['UID'] && form._dataMap['UID'].value;
    if (!bookingId) { showAlert('Сначала сохраните запись'); return; }

    var result = await callServer('__SERVER_SCRIPT__', 'calculateCost', { id: bookingId });
    if (result.error) { showAlert('Ошибка: ' + result.error); return; }
    // ... обновить ТЧ ...
    form.setModified(true);
}

return { sayHello, calculateCost };
```

### `init.js` — минимальная склейка

```javascript
'use strict';
const path = require('path');
const fs   = require('fs');

module.exports = async function (modelsDB) {
    try {
        const { loadScript, loadServerScript, Utilities } = require('../../node_modules/my-old-space');
        const layoutMemory = require('../../node_modules/my-old-space/drive_root/layoutMemory');

        // ── Форма <tableName> ────────────────────────────────────────────
        const serverScriptName = loadServerScript(
            '<appName>.<tableName>Actions',
            require('./forms/<tableName>.server')(modelsDB, Utilities),
            'user'
        );

        const clientSource = fs
            .readFileSync(path.join(__dirname, 'forms/<tableName>.client.js'), 'utf8')
            .replace(/__SERVER_SCRIPT__/g, serverScriptName);
        const clientUID = await loadScript(clientSource, 'user');

        await layoutMemory.saveLayout({
            appName:      'uniRecordForm',
            tableName:    '<tableName>',
            roles:        'user',
            layout:       require('./forms/<tableName>.layout.json'),
            clientScript: clientUID,
            events: {
                onBeforeSave: { serverScript: serverScriptName, fn: 'onBeforeSave' }
            }
        });

        // ── Добавить следующую форму по той же схеме ─────────────────────

        console.log('[<appName>/init] Layouts registered');
    } catch (e) {
        console.error('[<appName>/init] Failed:', e && e.message || e);
    }
};
```

### Несколько форм в одном приложении

Повторить паттерн для каждой формы: создать тройку файлов `<tableName2>.layout.json` + `.server.js` + `.client.js`, добавить блок в `init.js`:

```javascript
// Вторая форма — по аналогии
const server2Name = loadServerScript('<appName>.<tableName2>Actions',
    require('./forms/<tableName2>.server')(modelsDB, Utilities), 'user');
const client2Source = fs.readFileSync(path.join(__dirname, 'forms/<tableName2>.client.js'), 'utf8')
    .replace(/__SERVER_SCRIPT__/g, server2Name);
const client2UID = await loadScript(client2Source, 'user');
await layoutMemory.saveLayout({
    appName: 'uniRecordForm', tableName: '<tableName2>', roles: 'user',
    layout: require('./forms/<tableName2>.layout.json'),
    clientScript: client2UID,
    events: { onBeforeSave: { serverScript: server2Name, fn: 'onBeforeSave' } }
});
```

### Когда использовать монолитный init.js (старый стиль)

Монолитный стиль (всё инлайн в `init.js`) по-прежнему допустим когда:
- Форма очень простая (3-5 полей, 1-2 кнопки)
- Нет сложной серверной бизнес-логики
- Одна форма в приложении

Пример: `apps/booking_old/init.js` — рабочий образец монолитного стиля.

### Сравнение подходов

| Критерий | Монолитный (inline) | Раздельные файлы |
|---|---|---|
| Размер init.js | 100-300+ строк | ~25 строк |
| Тестируемость server.js | Нет | Да (можно require отдельно) |
| Правка лейаута | Нужен JS-редактор | Можно JSON-редактором |
| Подходит для | Простых форм | Средних и сложных форм |
| Пример | `apps/booking_old/init.js` | `apps/booking/` |

## 20. СИСТЕМА ИНТЕРНАЦИОНАЛИЗАЦИИ (i18n)

### Серверный i18n

- **Модуль:** `drive_root/i18n.js` — `loadI18n(projectRoot)`, `t(key, langCode)`, `tf(key, langCode, vars)`
- **Каскадные файлы переводов** (загружаются при старте, объединяются):
  - `node_modules/my-old-space/drive_root/i18n.json` — фреймворковые строки (~50 ключей: Alert, OK, Confirm, Yes, No, Loading..., месяцы, дни недели, все строки UI_classes.js)
  - `node_modules/my-old-space/drive_forms/i18n.json` — строки уровня forms
  - `apps/<appName>/i18n.json` — строки приложений
  - `<projectRoot>/i18n.json` — строки проекта
- **Сессионные хелперы** (`drive_forms/globalServerContext.js`): `tForSession(key, sessionID)`, `tfForSession(key, sessionID, vars)` — получают язык из сессии.
- **Язык пользователя:** хранится в `user_settings_string_values`, поле `Language`, кешируется в `getSessionContext(sessionID)`. Fallback: `'en'`.
- **Правило:** все пользователь-видимые строки в серверных файлах используют `tForSession`/`tfForSession`.

### Клиентский i18n — pipeline `serveFileFromPath`

Все статические JS-файлы из `resources/public/` проходят через `fileStore.serveFileFromPath(filePath, role, language)` (`drive_root/fileStore.js`).

**Три HTTP-роута используют `serveFileFromPath`:**
1. `/res/public/<path>` — `drive_root/server.js`
2. `/apps/<name>/resources/public/<path>` — `drive_root/server.js`
3. `/<appAlias>/res/public/<path>` — `drive_forms/server.js`
4. `globalServerContext.loadApps()` — при загрузке бандла `client.js` каждого приложения

**Pipeline внутри `serveFileFromPath`:**
```
fs.readFileSync(filePath)
  → optimizeJS()    // terser: { compress: true, mangle: false, output: { quote_style: 1 } }
  → translateJsMarkers(text, language)  // regex: /__t\((['"])([^'"]+)\1\)/g
  → _fileCache.set(`${filePath}|${role}|${language}`, result)
```

**КРИТИЧНО — `quote_style: 1`:**  
Терсер по умолчанию меняет одинарные кавычки на двойные → `__t('key')` становится `__t("key")` → regex не срабатывает → `__t` попадает в браузер → `ReferenceError` → `Draw()` молча падает → пустое серое окно. `output: { quote_style: 1 }` принудительно оставляет одинарные кавычки.

**Маркер `__t('key')` в `.client.js` файлах:**
```javascript
showAlert(__t('Please select a record'));
this._toolbar_label.textContent = __t('Loading...');
```
Браузер маркер НЕ видит. Ключ — сама английская строка (с пробелами, двоеточиями — разрешено).

**Кеш:** `_fileCache` (in-memory `Map`) — ключ `${filePath}|${role}|${language}`. Сбрасывается только перезапуском сервера.

### Перевод `caption` в лейаутах

- **Формат:** `"caption": { "i18n": "key" }` — объект вместо строки.
- **Механизм:** `getLayoutForUser(appName, tableName, userRole, sessionID)` в `drive_root/layoutMemory.js` — deep-clone + рекурсивная замена `{ i18n: key }` через `translateLayoutCaptions(layout, language)`. Обходит `layout`, `columns`, `options`.
- **Callers:** `uniListForm/server.js` и `uniRecordForm/server.js generateFormSpec()` — передают `sessionID`. Event-dispatch — НЕ передают.
- ❌ Не мутируй объект из `memoryStore.getSync()` — сначала deep-clone.

### Перевод справочных ДАННЫХ — таблица `translations` + `translationMiddleware`

Второй, отдельный от `i18n.json`, слой: перевод **значений полей записей** справочников (а не UI-подписей). Напр. `guest_types.name` («Adult» → «Dorosły»/«Erwachsener»), `booking_statuses.name`.

- **Модель:** таблица `translations` — `{ UID, recordId, tableName, fieldName, language, value }`. Сидируется через `defaultValues.json` (в проекте — `apps/common/db/defaultValues.json`).
- **Какие поля переводятся:** те, у кого в `db.json` стоит `"translatable": true`. `translationMiddleware._buildFieldsCache()` собирает их в `Map<tableName, fieldNames[]>` через `collectAllModelDefs()`.
- **Модуль:** `drive_root/translationMiddleware.js`. `install()` регистрирует middleware на `dbGateway.use('root', ...)`. Перехватывает READ-операции (`read/findOne/findByPk`), берёт язык из `getSessionContext(sessionID).language`, грузит переводы `(tableName, fieldName, language)` из таблицы `translations` и подменяет значения в результате.
- **Кэш:** `_valueCache: Map<"tableName|language", Map<"recordId|fieldName", value>>` — один запрос на пару (таблица, язык), сбрасывается `invalidateCache()`.
- **Пропуски (важно):** middleware НЕ переводит, если `sessionID === SYSTEM_SESSION_ID` (`__SYS_INTERNAL__`) или язык `'en'` (родной). **Следствие-ограничение:** FK-display в СПИСКАХ (`resolveTableForeignKeys` в `globalServerContext.js`) резолвится с `context: { sessionID: SYSTEM_SESSION_ID }` (чтобы обойти RLS) → значения справочников в FK-колонках списков остаются на родном (en), НЕ переводятся. Перевод FK-display потребовал бы резолвить имена с переводом, не открывая RLS — отдельная задача.
- **Добавление перевода справочника:** добавить строки в `translations` (`defaultValues.json`) на нужный язык; досев — `createDB` при старте.

### Язык ДОКУМЕНТОВ организации — `resolveOrgReportLang`

Счёт/отчёты печатаются на языке организации, а не пользователя. Резолвер: `apps/organizationSettings/lib/orgReportLanguage.js → resolveOrgReportLang(modelsDB, orgId)` — читает `organizationSettings → reportLanguage` (FK на `languages`) → код (`de`/`en`/`ru`/`pl`), дефолт `'de'`.

- **Консьюмеры (оба):** `apps/reports/init.js` (печать счёта — шапка через `i18n.t(key, lang)`, плюс маппинг локали `{ en:'en-GB', ru:'ru-RU', pl:'pl-PL', de:'de-DE' }`); `apps/booking/forms/bookings.server.js _buildInvoiceLines` (строки счёта — `tInv/tfInv`, привязанные к `i18n.t/tf(key, invLang)`). Оба берут язык из одного хелпера → шапка и строки на одном языке.
- Строки счёта **персистятся** в `InvoiceLines` при пересчёте, поэтому язык фиксируется на момент расчёта (старые счета перечитывают язык при следующем «Рассчитать стоимость»).

### Кэш `getLookupList` и язык (CRITICAL)

`getLookupList` (`drive_root/globalServerContext.js`) хранит УЖЕ переведённые (через translationMiddleware) display-значения выпадашек в `_lookupCache`. Ключ обязан включать язык: `` `${table}::${identity}::${language}::${firstRow}::${visibleRows}` `` (язык — из `getSessionContext(sessionID).language`). Без языка в ключе при смене языка в той же сессии возвращался устаревший перевод (баг «статусы по-русски при польском»). Свёрнутое значение recordSelector рисуется из этого же списка, поэтому баг бил и по нему.

### Порядок строк в `getLookupList`

`getLookupList` сортирует строки выпадашки `recordSelector` так: если у модели есть числовой атрибут `displayOrder` — `ORDER BY displayOrder ASC, UID ASC`; иначе — `ORDER BY UID ASC` (как было). Сортировать по `name` НЕЛЬЗЯ: в БД лежит английский base, перевод накладывается позже translationMiddleware → SQL-порядок был бы по чужому языку. UID-порядок = порядок создания, осмысленного порядка не даёт. Поэтому для «правильного» порядка справочника (напр. виды гостей по возрасту, взрослый первым) проставляй `displayOrder` в `defaultValues.json` — переставлять записи в массиве бесполезно. Это общий механизм: работает для любого справочника с полем `displayOrder`.

### Язык сессии и его инвалидация

`getSessionContext(sessionID).language` (`drive_forms/globalServerContext.js`) резолвит язык: настройка `Language` (FK на `languages`) → `languages.code`, дефолт `'en'`. Кэшируется (L1 Map + L2 store, ns `session_ctx`). После смены настроек **обязателен** `invalidateSessionContext(sessionID)` (его зовёт `UserSettings.saveSettings`), иначе язык/роль читаются из устаревшей копии. `UserSettings.saveSettings` дополнительно сравнивает старое/новое значение `Language` до upsert и возвращает `languageChanged` → клиент (`user_settings.client.js`) делает `location.reload()`.

### Поддерживаемые языки

`en`, `ru`, `de`, `pl` (`languages` UID `…lang-0001..0004`). Все каскадные `i18n.json` содержат эти 4 кода; отсутствие кода = тихий фолбэк на `en`. При добавлении языка — см. чеклист в разделе 2 `ИНСТРУКЦИИ_ДЛЯ_AI.md`.

### Шаблон счёта `apps/reports/invoice/template.js`
Все пользователь-видимые строки — через переданный `t(key)` (уже привязан к языку организации, см. «Язык документов организации»). **Раньше** шаблон был захардкожен на немецкий — теперь он мультиязычный; ключи — в `apps/reports/i18n.json` и `apps/booking/i18n.json`. `invoiceNote` (свободный текст из настроек) печатается как есть, без перевода.

## 21. ENTITY HOOKS — ХУКИ ЖИЗНЕННОГО ЦИКЛА ТАБЛИЦ

### Назначение

Система декларативных серверных хуков, срабатывающих при операциях с таблицей — независимо от источника (UI-форма, импорт, API, скрипт). В отличие от `onBeforeSave` формы, хуки таблицы работают всегда.

### Файловая структура

```
drive_root/
  entityHooks/
    index.js                  ← реестр: register(), resolve(), runHooks()
    default/
      autoNumber.js           ← встроенный: автонумерация документов
```

### Подключение в `db.json`

```json
{
  "name": "Bookings",
  "tableName": "bookings",
  "entityConfig": {
    "entityType": "document",
    "hooks": {
      "beforeCreate": [
        { "handler": "booking.onBeforeCreate" }
      ]
    }
  },
  "fields": { ... }
}
```

- `entityType`: `"document"` | `"directory"` (синонимы `catalog` / `справочник`) — тип **сущности**. Сущность системно (как UID) получает реквизит `number` + автонумерацию и поддерживает «представление» (поле `name`) — см. раздел 7 «Инъекция number» и подраздел «Представление сущности» ниже.
- `hooks.beforeCreate` — массив хуков перед `INSERT`; `hooks.beforeUpdate` — перед `UPDATE`.
- **`default.autoNumber` объявлять вручную НЕ нужно** — фреймворк авто-навешивает его на `number` всем сущностям. В `db.json` остаются только прикладные хуки (напр. `booking.onBeforeCreate`).

### Встроенные обработчики (`default.*`)

#### `default.autoNumber`

Автонумерация поля при создании записи. Алгоритм как в 1С:
1. Если поле уже заполнено — не трогает (пользователь ввёл вручную)
2. `SELECT MAX(field)` из таблицы (с опциональным фильтром периода)
3. Ищет **хвостовые цифры** в результате — всё до них сохраняется как префикс:
   - `"R00-01"` → prefix=`"R00-"`, digits=`"01"` → `"R00-02"`
   - `"00041"` → prefix=`""`, digits=`"00041"` → `"00042"`
   - `"ЙЦУК"` → нет цифр → `"ЙЦУК1"`
4. Длина числовой части сохраняется; при переполнении растёт (нет обрезки)
5. Первая запись (`MAX = null`) — формируется из `params`: `prefix + padStart(length, '0')`

> ⚠️ `params.prefix` и `params.length` влияют **только на самую первую запись** (пустая таблица).  
> Для последующих записей формат наследуется из фактического максимума.

**Параметры:**
| Параметр | Тип | По умолчанию | Описание |
|---|---|---|---|
| `field` | string | — | Имя поля (обязательно) |
| `length` | number | 5 | Длина числовой части **первой** записи |
| `prefix` | string | `""` | Префикс **первой** записи |
| `period` | null / `"year"` / `"month"` | `null` | Периодичность сброса счётчика |

### Пользовательские обработчики

Регистрация в `apps/<appName>/init.js`:
```js
const entityHooks = require('../../node_modules/my-old-space/drive_root/entityHooks');
entityHooks.register('booking.checkAvailability', require('./hooks/checkAvailability'));
```

Сигнатура обработчика:
```js
// apps/booking/hooks/checkAvailability.js
module.exports = async function(request, params, context) {
    // request.data  — данные записи (мутируем для изменений)
    // request.table — имя таблицы
    // params        — params из entityConfig (или {})
    // context       — { modelsDB, dbGateway }
};
```

Имя формата `"namespace.handlerName"` — просто соглашение, фреймворк префикс не парсит.

### Цепочка выполнения

```
dbGateway.execute({ operation: 'create' | 'update', ... })
  → app middleware (accessControl)
  → forms middleware
  → root middleware: entityHooksMiddleware
      → Model.entityConfig.hooks.beforeCreate / beforeUpdate
      → default.autoNumber(request, params, context)   // присваивает request.data.number
      → ...другие хуки...
      → entityHooks.applyPresentation(...)             // пишет request.data.name (ПОСЛЕ автонумерации)
  → executor → Model.create / Model.update
```
Middleware запускается для **любого** create/update, где есть `Model` (не только при наличии `entityConfig`) — чтобы `applyPresentation` срабатывал и для таблиц без хуков. `context = { modelsDB, dbGateway, sessionID }` (sessionID — из `request.context`).

### Представление сущности (поле `name`) — `registerPresentation` / `applyPresentation`
`name` сущности — это **«представление»** (наименование) записи: для документа — номер + ключевые реквизиты, для справочника — обычно введённое имя. Заполняется «спец-методом сущности», тело которого пишет прикладной программист.

- **Регистрация билдера** (в `apps/<app>/init.js`):
  ```js
  entityHooks.registerPresentation('bookings', async (data, ctx) => {
      // data — полные данные записи (на update — БД-запись, смерженная с изменениями;
      //        на create — данные новой записи, номер уже присвоен автонумерацией)
      // ctx  — { modelsDB, dbGateway, sessionID }
      return `${data.number} ${clientName} ${ci}–${co}`;
  });
  ```
- **Вызов** — `applyPresentation(operation, Model, request, context)` из middleware `dbGateway` ПОСЛЕ `runHooks` (т.е. после автонумерации), на каждом create/update. Пишет `request.data.name`. На update дочитывает текущую запись (`Model.findByPk`) и мерджит с изменениями. Нет билдера — **no-op** (для справочника опционален).
- **Где видно:** заголовок окна записи (`recordCaption + name`), колонка `name` в списках, FK-display. «Номерные»/печатные поля берут `number`, НЕ `name`.
- **Сиды на raw-SQL** (`tmp/generate_demo_base.js`, `defaultValues.json`) идут мимо middleware → `name`/`number` проставляются в самом сиде явно.

### Инжекция entityConfig на Model

В `globalServerContext.generateModelsFromDefs()` после `sequelize.define`:
```js
models[def.name].entityConfig = def.entityConfig || null;
```

Это делает `entityConfig` доступным в middleware через `Model.entityConfig`.

## 22. НАСТРОЙКИ ПО УМОЛЧАНИЮ (UserSettingsDefaults)

### Назначение

Позволяет каждому пользователю задать «запись по умолчанию» для любой таблицы базы данных. Например: «в форме бронирования гостиница по умолчанию — Zum Seiler».

### База данных: `user_settings_defaults`

| Поле         | Тип    | Описание                                      |
|---|---|---|
| `UID`        | STRING | PK, injected by events_handler.js            |
| `userId`     | STRING | FK → users.UID (обеспечивает RLS)             |
| `tableName`  | STRING | Машинное имя таблицы (e.g. `"hotels"`)        |
| `tableLabel` | STRING | Переведённое название таблицы (денормализация) |
| `recordId`   | STRING | UID записи в целевой таблице                  |
| `recordLabel`| STRING | Отображаемое имя записи (денормализация)       |

Уникальный индекс: `(userId, tableName)` — один дефолт на таблицу на пользователя.

Денормализация `tableLabel` и `recordLabel` позволяет отображать читаемые названия в DynamicTable без дополнительных JOIN-запросов.

### Файловая структура

```
apps/UserSettings/
├── init.js                           — регистрирует все 4 лейаута
├── forms/
│   ├── user_settings.server.js       — buildLayout() с кнопкой "Настройки по умолчанию"
│   ├── user_settings.client.js       — openDefaults()
│   ├── user_settings_defaults.server.js  — onLoadData_defaults, onSave_defaults, onLoadData_tableList
│   └── user_settings_defaults.client.js  — selectRecord, selectTableByDblClick
```

### Зарегистрированные лейауты (init.js)

| appName  | mode   | tableName                  | Назначение                              |
|---|---|---|---|
| uniForm  | record | user_settings              | Форма EAV-настроек (существующая)        |
| uniForm  | record | user_settings_defaults     | Форма редактирования одной записи-дефолта |
| uniForm  | list   | user_settings_defaults     | Список дефолтов (DynamicTable)           |
| uniForm  | record | user_settings_table_list   | Виртуальная форма выбора таблицы         |

### Виртуальная таблица `user_settings_table_list`

Не имеет DB-модели. Открывается как форма (mode='record') с кастомным `onLoadData_tableList`, который:
1. Вызывает `globalRootCtx.collectAllModelDefs()` для получения всех зарегистрированных таблиц
2. Фильтрует системные таблицы (`SYSTEM_TABLES` set)
3. Переводит названия через `tForSession(tableName, sessionID)`
4. Возвращает `data: [{ name: 'table_list', value: [{UID, tableLabel}], tabularSection: true }]`

Layout содержит plain `Table` (не DynamicTable) с pre-loaded данными. В select-режиме `getCurrentRow()` читает активную строку через `_activeRowIndex` + `data_getRows`.

## 23. ПОЛЕ ТИПА ADDRESS — АВТОЗАПОЛНЕНИЕ АДРЕСА (Google Places)

### Общее описание
Механизм автоматического подбора адреса при вводе в текстовое поле. Визуально — выпадающий список с предложениями (аналогично FK quick search). Использует Google Places Autocomplete API через официальный Google Maps JS SDK.

### Цепочка прохождения типа `address`

```
db.json → getTableMetadata() → buildTableFieldsFromModel() → клиент → renderItem → TextBox(addressMode:true) → Draw() → autocomplete
```

1. **`db.json`**: в определении поля добавить `"isAddress": true`
2. **`globalServerContext.getTableMetadata()`**: проставляет `isAddress` в объект метаданных поля (читается из `modelDef.fields[fieldName].isAddress`)
3. **`uniForm/server.js buildTableFieldsFromModel()`**: если `f.isAddress`, назначает `inputType = 'address'`
4. **`uniForm/server.js mapInputTypeToControl()`**: `'address'` → `'address'`
5. **`DataForm.renderItem()`**: `case 'address'` → создаёт `TextBox` с `properties.addressMode = true`
6. **`TextBox.Draw()`**: обнаруживает `this.addressMode`, устанавливает `this._addressEnabled = true`, вешает обработчик `_addrInputHandler`

### Отключение в кастомном лейауте
В `*.layout.json` указать `"type": "textbox"` для нужного поля — это переопределит `inputType = 'address'` с сервера.

### Google Maps JS API — ленивая загрузка
- API-ключ хранится только на сервере (в `.env` как `GOOGLE_PLACES_API_KEY`)
- Клиент получает ключ через `callServerMethod('uniForm', 'getPlacesConfig', {})`  
- Скрипт `https://maps.googleapis.com/maps/api/js?key=...&libraries=places` добавляется в `<head>` динамически при первом использовании
- Флаги `_placesReady`, `_placesLoading`, `_placesCallbacks` — module-level в `UI_classes.js`
- После загрузки вызывается глобальный callback `window._gmapsPlacesReady`

### Функции-помощники (module-level в UI_classes.js)
- `_ensureGooglePlaces()` — Promise, загружает Google Maps JS API, кэширует ключ
- `_getAddressPredictions(text)` — вызывает `AutocompleteService.getPlacePredictions({ input, types: ['address'] })`, возвращает `[{ description, placeId }]`
- `_getPlaceDetails(placeId)` — `PlacesService.getDetails({ fields: ['formatted_address'] })` → строка `formatted_address`
- **`window.MySpaceAddress.resolve(query)` / `.suggest(query)`** — публичный резолвер адреса поверх тех же функций (`predictions[0]` → `_getPlaceDetails` → `formatted_address`). Через него ИИ-агент (`ai_chat`) нормализует адрес тем же механизмом, что и поле AddressBox у человека — без отдельной среды.

### Поведение TextBox в режиме addressMode
- Ввод ≥ 3 символов → дебаунс 300мс → запрос к `_getAddressPredictions`
- Выпадающий список с предсказаниями — стиль идентичен FK quick search popup (`textbox-list-popup`)
- Навигация: ↑↓ стрелки, Enter — выбор, Escape — закрыть
- Клик по строке: `this.setText(description); this.text = description` → значение в БД = полный адрес (строка)
- Blur: **не** откатывает ввод (в отличие от FK quick search) — пользователь может вбить любой адрес вручную

### Серверная часть
- `uniForm/server.js::getPlacesConfig()` — возвращает `{ apiKey: process.env.GOOGLE_PLACES_API_KEY }`
- Ключ загружается из `.env` через `dotenv` (загружается в `index.js` проекта)
- Ключ **не** попадает в клиентский бандл при инициализации — только при первом focus на поле адреса

### Cleanup в destroy()
```javascript
try { if (this._addrDebounce) { clearTimeout(this._addrDebounce); this._addrDebounce = null; } } catch(e) {}
try { if (this._addrKeyCapture) { document.removeEventListener('keydown', this._addrKeyCapture, true); } } catch(e) {}
try { if (typeof this._closeAddrPopup === 'function') this._closeAddrPopup(); } catch(e) {}
```

### UX-сценарий

1. Пользователь открывает **Настройки пользователя** → видит кнопку **"Настройки по умолчанию"**
2. Открывается DynamicTable с `user_settings_defaults` (список дефолтов пользователя)
3. Кнопка **"Добавить"** → форма записи:
   - Поле **"Таблица"**: `recordSelector` → открывает `user_settings_table_list` в select-режиме
   - Кнопка **"Выбрать запись"**: открывает выбранную таблицу в select-режиме → заполняет `recordLabel`/`recordId`
4. **"ОК"** → `onSave_defaults` резолвит `tableLabel` и `recordLabel`, делает `upsert`

### Автозаполнение при открытии новой записи (DataForm)

**Реализовано в:** `apps/uniForm/server.js` → функция `generateFormSpec`

При открытии новой записи (`isNew = true`, нет `recordID/recordId/id` в params) `generateFormSpec` автоматически применяет значения из `UserSettingsDefaults` текущего пользователя.

#### Вспомогательные функции в `uniForm/server.js`

| Функция | Назначение |
|---|---|
| `loadUserDefaultValues(sessionID)` | Загружает `UserSettingsDefaults` пользователя из БД. Возвращает `Map<tableName, {recordId, recordLabel}>`. |
| `applyAutofillFromFields(data, fields, defaultsMap)` | Применяет дефолты по списку field-дефиниций (поля с `inputType === 'recordSelector'` и `foreignKey.table` или `properties.selection.table`). Используется для автогенерированных форм. |
| `applyAutofillFromLayout(data, layout, defaultsMap)` | Применяет дефолты, рекурсивно обходя лейаут в поиске элементов `type === 'recordSelector'` с `properties.selection.table`. Используется для кастомных форм с `onLoadData`. Пропускает динамические таблицы-ссылки (содержащие `{` в имени таблицы). |

#### Две точки вызова в `generateFormSpec`

1. **Custom форма с `onLoadData`** (ранний return) — вызывается `applyAutofillFromLayout` после получения данных от `onLoadData`, перед сохранением датасета:
   ```javascript
   if (!params || (!params.recordID && !params.recordId && !params.id)) {
       const dfltMap = await loadUserDefaultValues(sessionID);
       if (Object.keys(dfltMap).length > 0) applyAutofillFromLayout(data, layout, dfltMap);
   }
   ```

2. **Автогенерированная форма** (стандартный путь через `buildTableFieldsFromModel`) — вызывается `applyAutofillFromFields` после определения `isNew = true`:
   ```javascript
   if (isNew) {
       const dfltMap = await loadUserDefaultValues(sessionID);
       if (Object.keys(dfltMap).length > 0) applyAutofillFromFields(data, fields, dfltMap);
   }
   ```

#### Логика применения дефолта

- Заполняется только пустое поле (`item.value` falsy)
- Устанавливается как `item.value = def.recordId` и `item.selection = { id: def.recordId, display: def.recordLabel }`
- Поле `selection` обеспечивает корректное отображение display-значения в `recordSelector` контроле без дополнительных FK-запросов

## 24. ИКОНКИ ПРИЛОЖЕНИЙ — АРХИТЕКТУРА (formIcon)

### Назначение

Каждая открытая форма отображает иконку в заголовке окна и в кнопке таскбара. Система обеспечивает единый источник правды — `layoutMemory` для uniForm-приложений и `config.json` для standalone-приложений.

### Два типа приложений и их потоки

#### 1. uniForm-приложения (booking, user_settings, любой uniForm)

```
init.js saveLayout({ formIcon, appCaption })
  ↓ layoutMemory хранит formIcon + appCaption по tableName
  ↓ main_menu/server.js resolveMenuIcons() — читает layoutMemory при запросе меню
  ↓ main_menu/client.js buildAppIconRegistry() — строит window.MySpaceAppIcons
  ↓ uniForm/server.js getLayoutWithData() — возвращает formIcon + appCaption в ответе
  ↓ DataForm.loadLayout() — вызывает setFormIcon() + setTitle()
```

#### 2. Standalone-приложения (messenger, ai_chat и т.п.)

```
config.json — пункт меню с полем icon
  ↓ main_menu/server.js getMainMenuCommands() — передаёт icon из config.json as-is
  ↓ main_menu/client.js buildAppIconRegistry() — строит window.MySpaceAppIcons
  ↓ MySpace.open() — читает реестр, вызывает inst.setFormIcon() или inst.form.setFormIcon()
```

### `window.MySpaceAppIcons` — клиентский реестр иконок

Глобальный объект, строится `buildAppIconRegistry(rawItems)` в `main_menu/client.js` при получении меню.

**Ключи реестра:**
| Ключ | Условие | Пример |
|---|---|---|
| `appName` | Standalone app (нет `params.dbTable`) | `'messenger'` → `'/apps/general_icons/.../email.png'` |
| `appName:dbTable` | uniForm item (есть `params.dbTable`) | `'uniForm:bookings'` → `'/apps/booking_icons/.../booking_status.png'` |

**`MySpace.open()` применяет иконку** сразу после `createInstance()`:
```javascript
const key = (params && params.dbTable) ? `${name}:${params.dbTable}` : name;
const icon = (window.MySpaceAppIcons || {})[key];
if (icon) {
    const frm = (typeof inst.setFormIcon === 'function') ? inst
              : (inst.form && typeof inst.form.setFormIcon === 'function') ? inst.form
              : null;
    if (frm) frm.setFormIcon(icon);
}
```

> `inst` может быть формой напрямую (`uniForm` возвращает объект с `setFormIcon`) или объектом `{ form, ... }` (Messenger). Поэтому проверяются оба варианта.

### `resolveMenuIcons()` — ленивое разрешение иконок меню (сервер)

Вызывается в `main_menu/server.js` внутри `getMainMenuCommands()` **в рантайме** (не при старте), после того как все `init.js` приложений уже выполнены.

**Алгоритм для uniForm-пунктов** (item.appName === 'uniForm' && item.params.dbTable, нет item.icon):
1. `layoutMemory.getTableIcon(tableName)` → если задан явно → использовать
2. Иначе: читать `entityConfig.entityType` из `globalServerContext.collectAllModelDefs()`
   - `entityType === 'document'` → `/apps/general_icons/resources/public/16x16/document.png`
   - иначе → `/apps/general_icons/resources/public/16x16/catalog.png`

Для non-uniForm пунктов (standalone apps, ai_chat, etc.) — иконка уже задана в `config.json`, не меняется.

> **Важно: порядок инициализации.** Фреймворковые `init.js` (включая `uniForm/init.js`) запускаются **до** проектных (`booking/init.js`). Если бы разрешение иконок происходило в `uniForm/init.js` — иконки booking ещё не были бы зарегистрированы. Именно поэтому `resolveMenuIcons()` вызывается в рантайме при каждом запросе меню, а не при старте.

### `saveLayout({ formIcon, appCaption })` — регистрация иконки для таблицы

```javascript
await layoutMemory.saveLayout({
    appName:    'uniForm',
    tableName:  'bookings',
    roles:      'user',
    layout:     require('./forms/bookings.layout.json'),
    clientScript: clientUID,
    formIcon:   '/apps/booking_icons/resources/public/16x16/booking_status.png',
    appCaption: { i18n: 'bookings_app_caption' }, // или просто строка 'Бронирования'
    events:     { ... }
});
```

- `formIcon` — URL. Хранится в `_tableIcons[tableName]` в `layoutMemory`, доступен через `layoutMemory.getTableIcon(tableName)`
- `appCaption` — строка **или** `{ i18n: 'key' }`. Хранится в `_tableCaptions[tableName]`, доступен через `layoutMemory.getTableCaption(tableName)`. При возврате клиенту через `uniForm/server.js` значение с `i18n` переводится через `tForSession()`

### `uniForm/server.js` — передача иконки в ответе

Функция `getDefaultIconForTable(tableName)` в `uniForm/server.js`:
1. `layoutMemory.getTableIcon(tableName)` — если есть → вернуть
2. Иначе определить `entityType` → `document.png` или `catalog.png`

Все ветки `getLayoutWithData()` включают `formIcon` и `appCaption` в ответ. `DataForm.loadLayout()` применяет их через `setFormIcon()` и `setTitle()`.

### Итоговая матрица иконок

| Приложение | Откуда иконка берётся | Когда применяется |
|---|---|---|
| uniForm (booking, user_settings, ...) | `saveLayout({ formIcon })` → `layoutMemory` → `uniForm/server.js` ответ | В `DataForm.loadLayout()` при открытии формы |
| Standalone (messenger, ai_chat, ...) | `config.json` пункт меню → `buildAppIconRegistry()` | В `MySpace.open()` сразу после `createInstance()` |
| Обычная uniForm без кастомного лейаута | Fallback: `entityType === 'document'` → `document.png`; иначе → `catalog.png` | В `DataForm.loadLayout()` (автоматически из `uniForm/server.js`) |

## 25. ДИНАМИЧЕСКОЕ МЕНЮ — РЕГИСТРАЦИЯ, РОЛИ, ПЕРЕВОДЫ

### Два типа пунктов в `addMenuItems()`

**Тип 1 — пункт в выпадающем меню (кнопка с девятью квадратиками):**
Оберни в объект с `id: 'main'` — пункт попадёт в dropdown кнопки-грида.

```javascript
mainMenu.addMenuItems([{
    id: 'main',
    items: [{
        caption: { i18n: 'user_settings_app_caption' },
        action: 'open',
        singleton: true,
        appName: 'uniForm',
        params: { mode: 'record', dbTable: 'user_settings' }
    }]
}]);
```

**Тип 2 — отдельная кнопка в строке меню (рядом с кнопкой-сеткой):**
Передай объект с уникальным `id` без обёртки `id: 'main'` — станет самостоятельной кнопкой.

```javascript
mainMenu.addMenuItems([{
    id: 'bookings',
    caption: { i18n: 'bookings_app_caption' },
    action: 'open',
    singleton: true,
    appName: 'uniForm',
    params: { mode: 'list', dbTable: 'bookings' }
    // icon не указываем — resolveMenuIcons() возьмёт из layoutMemory
}]);
```

**Правила:**
- `icon` для uniForm-пунктов (`appName: 'uniForm'` + `params.dbTable`) **не указывать** — `resolveMenuIcons()` сам берёт из `layoutMemory.getTableIcon(tableName)`. Единственный источник правды — `formIcon` в `saveLayout()`.
- `icon` для standalone-пунктов (без `params.dbTable`) — указывается явно.

### i18n для фреймворковых приложений

Для приложений в `node_modules/my-old-space/apps/<Name>/` можно создать файл `i18n.json` прямо там — фреймворк автоматически его подхватит (loader сканирует все `apps/*/i18n.json`). Пример: `apps/UserSettings/i18n.json`.

### Ограничение по ролям (`roles`)

Поле `roles` на пункте меню ограничивает видимость по роли пользователя.

```javascript
{ caption: 'Администрирование', roles: ['admin'], items: [...] }
```

- Задаётся при регистрации (`addMenuItems()` в `init.js`) — **один раз при старте**.
- Фильтрация происходит **при каждом запросе меню** в `getMainMenuCommands()` через `filterItemsByRole(items, userRole)`.
- `filterItemsByRole()` рекурсивна: работает на любом уровне вложенности.
- Роль пользователя берётся из `getSessionContext(sessionID).role` (кэш в памяти).
- Пункты **без** `roles` — видны всем.

**ВАЖНО:** Пункт "apps" определён в **каждом** `config.json` фреймворковых приложений. Чтобы ограничить весь раздел "apps" только для admin — нужно добавить `"roles": ["admin"]` в каждый из этих файлов: `calculator`, `messenger`, `tetris`, `fileSystem`, `UserSettings`, `cpp_app` (в node_modules) и `ai_chat` (в проекте).

### Режим синглтона (`singleton: true`)

При `singleton: true` повторное открытие **не создаёт новое окно**, а активирует уже открытое.

**Реализация в `MySpace.open(name, params, options)`:**
- `options.singleton = true` → ключ `name:mode:dbTable`
- Поиск в `instances` по `inst._singletonKey`
- Если найден **и форма жива** (`document.contains(form.element)`) → `form.restore()` + `form.activate()`
- Если найден, но форма удалена из DOM → `delete instances[k]` → создаётся новый экземпляр
- Если не найден → создаётся новый, `inst._singletonKey` сохраняется

**Текущие singleton-пункты:**
- Бронирования: `{ id: 'bookings', ..., singleton: true, params: { mode: 'list', dbTable: 'bookings' } }`
- Настройки пользователя: `{ ..., singleton: true, params: { mode: 'record', dbTable: 'user_settings' } }`

### Закрытие формы: X, Escape, Cancel — поведение

**X-кнопка и Escape** → вызывают `this.close()` напрямую.  
`DataForm.close()` проверяет `_modified` и показывает "Save changes? Yes/No" (Yes — сохраняет, No — отбрасывает).

**Кнопка Cancel** → вызывает `this.doAction('cancel')`.  
`DataForm.doAction('cancel')` сначала пробует `instance.onAction('cancel', params)`. Если instance перехватил (вернул truthy) — выполняется его логика. Иначе — просто `this.close()`.

**В uniForm** `onAction('cancel')` перехватывает и показывает "Discard unsaved changes?" (только вопрос об отмене, без опции сохранения):
```
uniForm.onAction('cancel'):
  if (_modified) → showConfirm('Discard unsaved changes?')
    → on Yes: _closing=true, _modified=false, close()
  else → close() сразу
  return true  // перехвачено, DataForm.doAction останавливается
```

**Итог:**
| Действие | Диалог если `_modified` | Опция сохранения |
|---|---|---|
| X / Escape | "Save changes?" | Да (Yes/No) |
| Кнопка Cancel (uniForm) | "Discard unsaved changes?" | Нет (только Да/отмена) |

### Перевод caption (`{ i18n: 'key' }`)

Клиентский рендер меню (`main_menu/client.js`) использует `item.caption` напрямую как строку. Поэтому перевод выполняется **на сервере** при каждом запросе меню.

Функция `translateCaptions(items, sessionID)` в `main_menu/server.js`:
- Рекурсивно обходит дерево пунктов меню.
- Для каждого `caption` вида `{ i18n: 'key' }` вызывает `tForSession(key, sessionID)`.
- Мутирует items in-place.
- Вызывается после `filterItemsByRole()`, до `resolveMenuIcons()`.

### Порядок обработки в `getMainMenuCommands(params, sessionID)`

```
1. Собрать dynamicMenuItems (из addMenuItems) + config.json-пункты
2. filterItemsByRole(result, userRole)   — убрать пункты с ролью, недоступной пользователю
3. translateCaptions(filtered, sessionID) — перевести { i18n: 'key' } → строку
4. resolveMenuIcons(filtered)            — подставить иконки из layoutMemory
5. return filtered                       — отдать клиенту
```

### Антипаттерны

- ❌ Указывать `icon` в `addMenuItems()` для uniForm-пунктов — дублирует `formIcon` из `saveLayout()`.
- ❌ Добавлять перевод caption прямо в строку при старте (`caption: 'Бронирования'`) — язык пользователя неизвестен на старте.
- ❌ Проверять роль пользователя в `init.js` — он выполняется при старте, сессии нет.
- ❌ Добавлять `roles: ['admin']` только в один config.json — раздел "apps" дублируется в каждом фреймворковом приложении.
- ❌ Закрывать форму напрямую `this.close()` в X-кнопке или Escape — обходит диалог "Discard unsaved changes?". Всегда через `doAction('cancel', { isStandard: true })`.

## 26. ИИ-АССИСТЕНТ (ai_chat) — АГЕНТ, УПРАВЛЯЮЩИЙ UI

`apps/ai_chat` — чат-ассистент на внешней модели **Google Gemini**, который управляет интерфейсом как человек (открывает формы, заполняет поля, жмёт кнопки) через **function calling**. Голос и вложения (картинка/PDF) — мультимодально той же моделью.

### Ключевой принцип (CRITICAL)
Агент действует **теми же обработчиками/контролами/формами, что и человек** — никакой параллельной логики «для ИИ». Программная вставка строки → вызвать `activateRow` (срабатывают те же события, напр. дефолтные услуги); создать запись → обычной формой (`open_form`/`fill`/`save`), не прямым INSERT; адрес → тем же резолвером Google Places, что и AddressBox.

### Серверный прокси — `apps/ai_chat/forms/chat.server.js`
Регистрируется в `init.js`: `loadServerScript('ai_chat.gemini', module, 'user')`. Ключ Gemini и модель — только на сервере в `ai_settings.json` (корень проекта, git-ignored): `{ geminiApiKey, geminiModel }`. `readSettings()` перечитывает файл на каждый вызов → смена модели без рестарта. Модель сейчас `gemini-2.5-pro` (`gemini-2.0-flash` ретайрнут). Клиент зовёт методы через `callServer('ai_chat.gemini', fn, params)`:

| Метод | Назначение |
|---|---|
| `sendMessage` | простой текстовый чат без инструментов (legacy) |
| `transcribe({audioBase64, mimeType})` | распознавание речи: аудио → текст самой моделью (`inlineData`) |
| `agentStep(...)` | один шаг агента с function calling |
| `getConversation()` | история сообщений (для показа) + память при открытии окна |
| `remember({text})` / `forget({text})` | долговременная память фактов |

### Function calling — протокол (проверено эмпирически)
- Запрос: `tools: [{ functionDeclarations: [...] }]` + `systemInstruction`.
- Ответ модели — часть `{ functionCall: { name, args } }` (+ `thoughtSignature` у 2.5-thinking).
- Ответ на инструмент: контент `role: 'user'`, часть `{ functionResponse: { name, response } }`.
- В историю кладётся **сырой `candidate.content`** модели (с `thoughtSignature`), не реконструировать.

### Агентный цикл (клиент ведёт, сервер владеет контекстом)
`agentStep(params, ctx)`, `params = { history?, userMessage?, toolResults?, attachment? }`:
1. **userMessage** (начало хода): сервер фиксирует сообщение в `ai_chat_messages`, строит `history` из несвёрнутого «хвоста» сообщений в БД; вложение → добавляется `inlineData`-частью к текущему user-turn'у.
2. **toolResults** (продолжение): использует переданный `history`, добавляет `functionResponse`-части, снова зовёт Gemini.
3. На `done`: сохраняет ответ ассистента + `maybeSummarize`.

Клиент: первый шаг шлёт `{userMessage}` (+attachment), дальше `{toolResults, history}`. Системный промпт каждый раз = факты + пересказ (память) + список открываемых форм (из `main_menu.getMainMenuCommands`, фильтр по роли) + сегодняшняя дата.

### BotAPI (клиент, `client.js`) — инструменты → примитивы фреймворка
Каждый tool выполняется в браузере и дёргает штатные механизмы:

| Tool | Реализация |
|---|---|
| `open_form({table, mode, recordId})` | `MySpace.open('uniForm', {mode, tableName/dbTable, recordID})` → ждёт отрисовки → `read_form_state` |
| `read_form_state()` | `form.collectData()` (значения) + обход `form.layout` (поля/типы/refTable, кнопки, табличные части с текущими строками) |
| `fill_field({name, value})` | скаляр → `ctrl.setValue`; ссылка (recordSelector) → резолв по имени через `quickSearch` → `setValue(UID, display)`; адрес → `window.MySpaceAddress.resolve` |
| `find_records({table, query})` | `callServerMethod('uniForm','quickSearch', {tableName, searchText, displayField})` (RLS-aware) |
| `add_table_row({table, fields})` | `data_getRows`→push→`data_updateValue`→`_invokeRenderBodyRows`; UID через `drive_api.getNewUID`; FK-колонки резолвятся; затем **`activateRow(newIndex)`** → `onRowActivate` (дефолтные услуги, masterFor); detail-строки авто-привязка к мастеру по `masterFor`/`detailField` |
| `remove_table_row({table,index})` / `clear_table({table})` | splice/clear + ререндер; каскадно удаляет detail-строки мастера |
| `save_form()` / `click_button({action})` | `collectData()`+`__tabularSections`→`form.applyChanges()` (с результатом); либо `form.doAction('save'/'ok'/'cancel'/<custom>)` |
| `remember/forget({text})` | серверная долговременная память |
| `list_windows()` / `focus_window({id})` | `MySpace.listInstances()` / `getInstance(id)`+`form.activate()` — осведомлённость об окнах и переключение между формами (мультиформенные сценарии) |

### Память (на пользователя, RLS по `userId`)
Модели в `apps/ai_chat/db/db.json`: `ai_chat_messages` (userId, role, text, timestamps) — полный лог; `ai_chat_memory` (userId, summary, facts(JSON), summarizedCount) — память. Три слоя:
1. Последние `KEEP_VERBATIM`=16 сообщений — дословно (буфер = сообщения после `summarizedCount`).
2. `maybeSummarize`: когда несвёрнутых > ~24, старшие сворачиваются в `summary` отдельным LLM-вызовом, `summarizedCount` двигается (нет разрыва/дублей).
3. `facts` — модель ведёт сама через `remember`/`forget` (дедуп, лимит 40), всегда в системном промпте.

`saveMemory(patch)` пишет **только переданные поля** (иначе `{summary}` затрёт `facts`).

### Окно ассистента
Правый нижний угол, **над таскбаром** (`positionBottomRight` резервирует `Form.bottomOffset`, которую задаёт приложение `taskbar`). **Поверх всех окон** (`activate` форсит `z=9999`) — но ниже системных попапов (≥10000), чтобы диалоги/выпадашки оставались кликабельны.

### Правки во фреймворке, сделанные для агента (нужно влить в апстрим)
- `MySpace.listInstances()` (UI_classes.js) — список живых окон `[{id, appName, title, tableName}]`.
- `window.MySpaceAddress.resolve/suggest` (UI_classes.js, рядом с `_getAddressPredictions`) — публичный резолвер адреса поверх тех же Places-функций, что и AddressBox.
- `uniForm.quickSearch` принимает `displayField` (доверяется, если атрибут существует; авто-выбор пропускает UID/таймстемпы — старая `isString`-проверка через `.type.key` ненадёжна и роняла поиск комнат на `UID`), возвращает `{items, displayField}`.

## 27. ЭЛЕМЕНТ ФОРМЫ `calendar` — ШАХМАТКА ЗАНЯТОСТИ (resource × time)

Переиспользуемый фреймворк-элемент (`class Calendar extends UIObject` в `UI_classes.js`,
`case 'calendar'` в `DataForm.renderItem`). Декларативно-конфигурируемый — не привязан к
booking; booking лишь поставляет конфиг и серверный загрузчик. Применён на **кастомной
форме списка броней** (вкладка «Календарь» рядом со списком; см. ниже).

### Конфиг (layout `properties`)
- `resourceField` — поле события, дающее дорожку-ресурс (booking: `resourceId` = комната);
- `startField`/`endField` — даты начала/конца (DATEONLY `'YYYY-MM-DD'`), booking: `start`/`end`;
- `labelField` — подпись полосы (booking: `label` = имя клиента); `colorField` — цвет (`#rrggbb`);
- `idField` — идентификатор записи для open/select (по умолч. `UID`);
- `tableName` — таблица записи (open/select/add через `uniForm`);
- `serverScript` + `loadFn` — имя RPC-скрипта и метод загрузки данных. **Имя `serverScript`
  внедряется в свойства календаря в `init.js`** (обход лейаута, поиск `type:'calendar'`) —
  аналогично подстановке `__SERVER_SCRIPT__` в клиентских файлах;
- `orientation` — `'horizontal'` (даты по X, ресурсы-строки; по умолчанию) | `'vertical'`;
- `hiddenButtons` — скрыть действия тулбара (`prev/next/today/orientation/recordAdd/recordOpen/recordDelete/select/cancel`).

### Данные (контракт `loadCalendar`)
Контрол сам тянет данные `window.callServer(serverScript, loadFn, { hotelId, from, to })`
(не через onLoadData формы — список самодостаточен). Ответ:
`{ hotels:[{UID,name}], hotelId, rooms:[{UID,number}], events:[{UID,resourceId,start,end,label,color,raw}], from, to, orientation }`.
Серверный `loadCalendar` (`apps/booking/forms/bookings_list.server.js`) читает всё через
**dbGateway с `context.sessionID`** (RLS сам фильтрует по отелям/организациям пользователя):
отели → селектор; комнаты выбранного отеля; брони отеля, пересекающие окно; привязки
`booking_rooms` → одна полоса-событие на (бронь × комната этого отеля). **Брони без
комнаты в календаре не показываются.** Цвет — из `booking_statuses.color`, имя — из `clients.name`.

### Модель «ночи» и геометрия
Единица — **ночь**. Полоса — прямоугольник от **середины** дня заезда до **середины** дня
выезда (смещение на полклетки): `left = (startIdx + 0.5) * step`, `width = nights * step`
(обрезается по окну). В день смены уезжающая бронь занимает левую половину клетки, приезжающая —
правую (встык через зазор 1px) — классическая PMS-шахматка, но **без диагоналей** (обычные
прямоугольники: раз стык и так на середине дня, диагональ избыточна). Двойной клик по пустой
ячейке — новая бронь с этой даты как датой заезда.

Каркас — **строково-слоевой** (НЕ CSS-grid) в скролл-контейнере: `.ui-calendar-headrow`
(sticky `top:0`, ячейки оси абсолютно, угол `.ui-calendar-corner` sticky `left:0`) над
`.ui-calendar-bodywrap`, внутри которого `.ui-calendar-overlay` (абсолютный слой полос+сетки,
`left:labelW`) и `.ui-calendar-gutter` (sticky `left:0`, один элемент во всю высоту тела, подписи
абсолютно). **Почему не grid:** у sticky-ячейки в CSS-grid containing block — её узкий трек
(`labelW`), поэтому при горизонтальном скролле дальше `labelW` подписи «уезжали». В слоевой
раскладке containing block жёлоба/шапки — во всю ширину/высоту, sticky приклеен на всём протяжении.
Геометрия унифицирована: ось времени = `step`, ось ресурса = `lane`; `horizontal` → time→X/res→Y,
`vertical` → time→Y/res→X. CSS — `.ui-calendar*` в `style.css` (фон-сетка градиентами; подсветка
сегодня/выходных). При открытии — прокрутка к сегодня (`_scrollToToday`).

**Адаптивность:** `lane` (высота строки-комнаты / ширина столбца) авто-растягивается под
доступный размер контейнера, когда ресурсов мало (иначе узкая полоска сверху и пустота), с
пределом `laneMax`; полоса растягивается на высоту дорожки (поля `marginCross` по краям).
Пересчёт — через `ResizeObserver` на скролл-контейнере (`_scheduleRelayout`, дебаунс), который
также перематывает к сегодня при появлении вкладки из `display:none` (когда размер был 0).

Вкладки списка растягиваются на всю высоту формы через режим `fillHeight` элемента `tabs`
(класс `.ui-tabs-fill`): панель, её контент и активная вкладка получают `flex:1`, фиксация
`minHeight` по контенту пропускается — иначе (как у формы записи с полями) вкладки размерятся
по контенту и таблица/календарь не заполнят окно.

### Взаимодействие
- **Двойной клик по полосе** → тот же путь, что `DynamicTable.onSelectOrOpen`: в `selectMode`
  ставит `appForm._currentRecord` и зовёт `appForm.onSelect({})`; иначе `MySpace.open('uniForm',
  {mode:'record', tableName, recordID})` + reload по `form-destroyed`.
- **Двойной клик по пустой ячейке** / кнопка «Добавить» → `MySpace.open('uniForm',
  {mode:'record', tableName, prefill:{ checkIn, hotelId }, prefillTabular:{ booking_rooms:[{roomId}] }})`.
- Тулбар на `new Button()` (Win95): отель-`<select>`, Сегодня, поворот ориентации, Добавить/
  Открыть/Удалить; **Выбрать/Отмена — только в `selectMode`** (читается `this.appForm.selectMode`).
  Удаление — `callServerMethod('uniForm','deleteRecord',{tableName,recordId})` + `showConfirm`.
- `destroy()` — снимает `ResizeObserver`/таймеры и DOM (слушатели `form-destroyed` одноразовые).

### Прокрутка и диапазон дат
- **Колесо мыши** в горизонтальном календаре крутит по горизонтали (`wheel` → `scrollLeft += deltaY`,
  `preventDefault`); в вертикальном — натуральный вертикальный скролл.
- **Диапазон авто-расширяется** при скролле к краю (`_onScroll` → `_extendWindow('past'|'future')`,
  сдвигает `fromDate`/`toDate` на `_extendChunk` и перезапрашивает) — бесконечная лента без кнопок
  ←/→. При расширении влево к позиции добавляется `chunk*step` (`_pendingScrollDelta`), чтобы вид
  не «прыгал». Флаг `_extending` защищает от повторного входа во время загрузки.
- **Позиция скролла сохраняется** между перерисовками. К «сегодня» перематываем только при первом
  показе (или по `_forceToday`: кнопка «Сегодня», смена ориентации). `_renderPreservingScroll`
  запоминает `scrollLeft/Top` до `_renderGrid` и восстанавливает после; `_scheduleRelayout`
  пропускает пересборку, если размер не изменился (переключение вкладки `visibility`) — раньше
  перезагрузка после правки брони и переход между вкладками сбрасывали скролл в стартовое положение.

### Кастомная форма списка броней (вкладки)
`apps/booking/forms/bookings_list.layout.json` — элемент `tabs`: вкладка 1 «Список» = точная
копия дефолтного list-`DynamicTable` (полный паритет: Add/Open/Delete/сортировка/SSE/`selectMode`
встроены), вкладка 2 «Календарь» = элемент `calendar`. Регистрируется в `init.js` как
`layoutMemory.saveLayout({ appName:'uniForm', mode:'list', tableName:'bookings', layout, listIcon, appCaption })`
— **без `clientScript`** (календарь самодостаточен). Та же форма используется и как форма
ВЫБОРА брони (`selectMode`) — обе вкладки поддерживают выбор автоматически.

## 28. ЦВЕТ КАК first-class `inputType` + контрол `Color`

Поле в `db.json` может задать кастомный UI-контрол через `"inputType": "<тип>"` (по аналогии с
`isAddress`). Цепочка: `getTableMetadata` (`globalServerContext.js`) читает
`modelDef.fields[f].inputType` → кладёт в метаданные → `uniForm.buildTableFieldsFromModel`
предпочитает явный `f.inputType` (иначе маппинг по типу Sequelize) → `mapInputTypeToControl`
(добавлен `color`) → `renderItem case 'color'`. Контрол `class Color extends FormInput`
(`UI_classes.js`) — Win95-обёртка над `<input type="color">` + hex-подпись; хранит/возвращает
`#rrggbb`; CSS `.ui-color*`. Применение: `booking_statuses.color` (`apps/common/db/db.json`,
`inputType:'color'`) — автогенерируемая форма справочника сама показывает пикер; дефолтные
цвета — `apps/common/db/defaultValues.json`; идемпотентный патч существующих баз —
`tmp/generate_demo_base.lib.js` (`ALTER TABLE ... ADD COLUMN IF NOT EXISTS color` + `UPDATE ... WHERE color IS NULL`).

## 29. `prefill` / `prefillTabular` — ПРЕДЗАПОЛНЕНИЕ НОВОЙ ЗАПИСИ (uniForm)

`generateFormSpec` (`apps/uniForm/server.js`) для **новой** записи (`isNew`) применяет параметры
открытия:
- `params.prefill = { field: value }` — проставляет начальные значения скалярных полей (приоритет
  над автозаполнением); для FK-полей резолвит `selection.display` через `dbGateway.findByPk`, чтобы
  поле сразу показало имя, а не UID;
- `params.prefillTabular = { <ts_table>: [ {…строки} ] }` — засевает строки табличной части новой
  записи (UID строк генерируется `util.generateUID(tsDef.name)`); FK-display строк резолвится
  существующим блоком резолва ТЧ. Путь сохранения тот же, что у вручную добавленных строк.

Используется календарём («добавить бронь с уже выбранными комнатой и датой заезда»), но механизм
общий для любого `MySpace.open('uniForm', { mode:'record', tableName, prefill, prefillTabular })`.
